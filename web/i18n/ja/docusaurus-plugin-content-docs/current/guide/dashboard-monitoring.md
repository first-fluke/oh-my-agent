# ダッシュボード監視

## 2つのダッシュボードコマンド

oh-my-agentには、マルチエージェントワークフロー中のエージェント活動を監視するリアルタイムダッシュボードが2つあります。

| コマンド | インターフェース | URL | 技術 |
|:--------|:---------|:----|:-----------|
| `oma dashboard terminal` | ターミナル（TUI） | N/A（ターミナルに表示） | chokidarファイルウォッチャー、picocolorsレンダリング |
| `oma dashboard web` | ブラウザー | `http://127.0.0.1:9847/`（起動時に表示） | HTTPサーバー、WebSocket、chokidarファイルウォッチャー |

両方のダッシュボードはデフォルトでカレントディレクトリ配下の`.agents/state/memories/`を監視します。別のプロジェクトを監視するには`--project-root <path>`を渡し、調整用ファイルが別の場所にある場合は`MEMORIES_DIR`を設定します。ダッシュボードは`.serena/memories/`へ自動的にフォールバックしません。

### ターミナルダッシュボード

```bash
oma dashboard terminal
```

ターミナルに罫線で構成されたUIを直接表示します。メモリファイルが変更されると自動的に更新されます。終了するには`Ctrl+C`を押します。画面は上から順に4つの領域で構成されます。

| 領域 | 表示内容 | ソース |
|:-------|:------|:-------|
| ヘッダー | `OMA Memory Dashboard`と`Session: <id> [<status>]` | `orchestrator-session.md`、なければ最新の`session-*.md`。どちらもなければ`N/A [UNKNOWN]` |
| エージェントテーブル | Agent、Status、Turn、Task（先頭20文字）。空の場合は`No agents detected yet` | `task-board.md`、なければメモリファイルから検出したエージェント |
| Latest Activity | 最大5行の`[<name>] <message>`。空の場合は`No activity yet` | 更新日時が新しい5つの`.md`ファイルの最後の意味のある行 |
| フッター | `Updated: <time>  \|  Ctrl+C to exit` | 最後に再描画した時刻 |

**ステータス記号：**
- `●`（緑）：running
- `✓`（シアン）：completed
- `✗`（赤）：failed
- `○`（黄）：blocked
- `◌`（薄色）：pending

### Webダッシュボード

```bash
oma dashboard web
```

ループバック専用のWebサーバーをポート9847で起動します（`DASHBOARD_PORT`で変更可能）。コマンドは`http://127.0.0.1:9847/`と`Watching: <memories dir>`を表示します。起動のたびに新しいアクセストークンが作成され、配信するページに埋め込まれるため、表示されたURLを開くだけで済み、コピーするものはありません。ページは`/api/state`、`/api/recap`、WebSocketのリクエストでトークンを送信します。トークンなしのリクエストは`401`を返します。

```bash
# Custom port
DASHBOARD_PORT=8080 oma dashboard web

# Custom memories directory
MEMORIES_DIR=/path/to/.agents/state/memories oma dashboard web

# Recap view from the same process: http://127.0.0.1:9847/recap
```

Webダッシュボードはターミナルダッシュボードと同じ情報を、次の要素を備えたスタイル付きのダークテーマUIで表示します。

- 接続ステータスバッジ（Connected / Disconnected / Connecting、自動再接続付き）
- セッションIDとステータスバー
- ステータスドットをアニメーション表示するエージェントステータステーブル
- 最新アクティビティフィード
- 自動更新されるタイムスタンプ

## 推奨する3ターミナル構成

マルチエージェントワークフローでは、3つのターミナルペインを使う構成を推奨します。

| ペイン | 実行するもの | 目的 |
|:-----|:----|:--------|
| 1. メインエージェント | ホストのCLI（`claude`、`codex`、`agy`、`qwen`など）を起動し、`/orchestrate`または`/work`を実行 | ワークフローを進める |
| 2. ダッシュボード | `oma dashboard terminal`（または`oma dashboard web`） | 進捗をパッシブに監視する。操作なしで更新される |
| 3. 臨時のコマンド | `oma agent status session-20260324-143052 backend frontend`、`oma stats get`、`oma verify agent backend -w ./api` | エージェントの状態確認、検証の実行、統計の表示、問題のデバッグ |

## `.agents/state/memories/`のデータソース

ダッシュボードは`.agents/state/memories/`ディレクトリを読み取ります。このディレクトリには、実行中にエージェントとワークフローが調整用ファイルを書き込みます。状態が別の場所に保存されているプロジェクトでは、`MEMORIES_DIR`を使います。

### ファイルの種類と内容

| ファイルパターン | 作成元 | 内容 |
|:-------------|:----------|:---------|
| `orchestrator-session.md` | `/orchestrate` Step 2 | セッションID、開始時刻、状態（RUNNING/COMPLETED/FAILED）、ワークフローのバージョン |
| `session-{workflow}.md` | `/work`、`/ultrawork` | セッションのメタデータ、フェーズの進捗、ユーザーリクエストの概要 |
| `task-board.md` | オーケストレーションワークフロー | エージェントの割り当て、状態、タスクを示すMarkdownテーブル |
| `progress-{agent}.md` | スポーンされた各エージェント | 現在のターン番号、作業内容、中間結果 |
| `result-{agent}.md` | 完了した各エージェント | 最終状態（COMPLETED/FAILED）、変更ファイル、発見した問題、成果物 |
| `debug-{id}.md` | `/debug`ワークフロー | バグの診断、根本原因、適用した修正、回帰テストの場所 |
| `experiment-ledger-{sessionId}.md` | 実際の実験 | 比較可能なベースラインと候補の証拠、必須チェック、判断 |
| `lessons-{sessionId}.md` | 再利用できる原因が証拠で裏づけられた場合 | セッション単位の教訓。スコアによる自動生成はありません |

### ダッシュボードの読み取り方法

ダッシュボードは、情報を抽出するために複数の方法を使います。

1. **セッション検出**：まず`orchestrator-session.md`を探し、なければ更新日時が最も新しい`session-*.md`にフォールバックします。キーワード`RUNNING`、`IN PROGRESS`、`COMPLETED`、`DONE`、`FAILED`、`ERROR`から状態を解析します。
2. **タスクボードの解析**：`task-board.md`をMarkdownテーブルとして読み取ります。列からエージェント名、状態、タスクの説明を抽出します。
3. **エージェントの検出**：タスクボードがない場合は、すべての`.md`ファイルをスキャンし、`**Agent**: {name}`パターン、`Agent: {name}`行、または`_agent`や`-agent`を含むファイル名からエージェントを見つけます。
4. **ターン数のカウント**：検出した各エージェントについて、`progress-{agent}.md`を読み、`turn: N`パターンからターン番号を抽出します。
5. **アクティビティフィード**：更新日時が新しい`.md`ファイルを5件並べ、最後の意味のある行（見出し、ステータス行、アクション項目）をアクティビティメッセージとして抽出します。Webダッシュボードは`/recap`でリキャップ表示も提供します。

## 各ダッシュボードの表示内容

### セッションの状態

上部には次の内容が表示されます。

- **セッションID**：セッションファイルから抽出します（形式：`session-YYYYMMDD-HHMMSS`）。
- **状態**：色で分類します。RUNNINGは緑、COMPLETEDはシアン、FAILEDは赤、UNKNOWNは黄です。

### タスクボード

エージェントテーブルには、検出された各エージェントについて次の内容が表示されます。

- **エージェント名**：ドメイン識別子（backend、frontend、mobile、qa、debug、pm）。
- **状態**：視覚的な表示を伴う現在の状態（running/completed/failed/blocked/pending）。
- **ターン**：エージェントの現在のターン番号（完了した反復回数）。進捗ファイルから抽出します。
- **タスク**：エージェントが処理している内容の短い説明（表示幅に合わせて切り詰めます）。

### エージェントの進捗

進捗は`progress-{agent}.md`ファイルで追跡します。各ファイルはエージェントが作業するたびに更新されます。ダッシュボードはこれらのファイルをポーリングして、次を読み取ります。

- ターン番号（エージェントの進行に合わせて増加）
- 現在のアクション（エージェントが今行っていること）
- 中間結果（部分的に完了した内容）

### 結果

エージェントが完了すると、`result-{agent}.md`に次の内容を書き込みます。

- 最終状態（COMPLETEDまたはFAILED）
- 変更ファイルの一覧
- 発生した問題
- 作成した成果物

このファイルが存在すると、ダッシュボードは完了を検出してエージェントの状態を更新します。

## トラブルシューティング手順 {#troubleshooting-runbook}

### シグナル1：エージェントが「running」だがターンが進まない

**症状：** ダッシュボードではエージェントがrunningですが、数分経ってもターン番号が変わりません。

**考えられる原因：**
- エージェントが長時間の処理（大規模なコードベースのスキャン、遅いAPI呼び出し）で停止している
- エージェントがクラッシュしたが、PIDファイルが残っている
- エージェントがユーザー入力を待っている（自動承認モードでは発生しないはずです）

**対応：**
1. エージェントのログファイルを確認します。`oma agent spawn`はそのパスを`Log: ...`として表示します。ファイルはOSの一時ディレクトリにあります：`cat "${TMPDIR:-/tmp}/subagent-{session-id}-{agent-id}.log"`
2. プロセスが実際に動いているか確認します：`oma agent status {session-id} {agent-id}`
3. プロセスが動いていないのに状態がrunningなら、エージェントはクラッシュしています。エラーのコンテキストを付けて再スポーンします。

### シグナル2：エージェントが「crashed」と表示される

**症状：** `oma agent status`がエージェントについて`crashed`を返します。

**考えられる原因：**
- CLIベンダープロセスが予期せず終了した（メモリ不足、APIクォータ超過、ネットワークタイムアウト）
- ワークスペースディレクトリが削除された、または権限が変更された
- ベンダーCLIがインストールされていない、または認証されていない

**対応：**
1. ログファイルで詳細を確認します：`cat "${TMPDIR:-/tmp}/subagent-{session-id}-{agent-id}.log"`（`oma agent spawn`が表示する`Log:`のパス）
2. CLIのインストールを確認します：`oma doctor`
3. 認証を確認します：`oma auth status`
4. 同じタスクでエージェントを再スポーンします：`oma agent spawn {agent-id} "{task}" {session-id} -w {workspace}`

### シグナル3：「エージェントがまだ検出されていません」と表示される

**症状：** ダッシュボードは動作していますが、エージェントが表示されません。

**考えられる原因：**
- ワークフローがまだエージェントのスポーン段階に到達していない
- `.agents/state/memories/`ディレクトリが空である
- ダッシュボードが誤ったディレクトリを監視している

**対応：**
1. メモリディレクトリを確認します：`ls -la .agents/state/memories/`
2. ワークフローがまだ計画段階か確認します（エージェントがまだスポーンされていない可能性があります）。
3. ダッシュボードが正しいプロジェクトディレクトリを監視していることを確認します。ダッシュボードは現在の作業ディレクトリからメモリパスを解決します。プロジェクトルートから実行するか、`--project-root /path/to/project`を渡します。`oma dashboard web`は監視中のパスを`Watching: <path>`として表示します。
4. カスタムパスを使う場合：`MEMORIES_DIR=/path/to/.agents/state/memories oma dashboard terminal`

### シグナル4：Webダッシュボードが「disconnected」と表示される

**症状：** Webダッシュボードの接続バッジが赤色の「Disconnected」になります。

**考えられる原因：**
- `oma dashboard web`プロセスが終了した
- `oma dashboard web`プロセスが再起動され、開いているタブが以前のプロセスのトークンを保持したままになっている

**対応：**
1. ダッシュボードプロセスが動いているか確認します：`ps aux | grep dashboard`
2. ダッシュボードを再起動した場合は、ページを再読み込みして新しいトークンを取得させます。
3. プロセスが停止している場合は、`oma dashboard web`を再度起動してからページを再読み込みします。
4. 起動時に`Dashboard failed: port 9847 is already in use`で失敗する場合は、ポートを確認し（`lsof -i :9847`）、別のポートを試します：`DASHBOARD_PORT=8080 oma dashboard web`
5. Webダッシュボードは指数バックオフ（1秒から始まり最大10秒）で自動再接続します。数秒待って再接続を確認します。

## マージ前の監視チェックリスト

ダッシュボードで次を確認してから、マルチエージェントセッションの完了を判断します。

- [ ] **すべてのエージェントが「completed」**：runningまたはblockedで停止しているエージェントがない
- [ ] **「failed」のエージェントがない**：あればログを確認して再スポーンする
- [ ] **QAエージェントがレビューを完了**：`result-qa-agent.md`または`result-qa.md`を確認する
- [ ] **CRITICAL/HIGHの指摘がゼロ**：QAの結果ファイルで重要度ごとの件数を確認する
- [ ] **セッション状態がCOMPLETED**：セッションファイルに最終状態が表示されている
- [ ] **アクティビティフィードに最終レポートがある**：最後のアクティビティが概要レポートになっている

---

## 完了条件

ダッシュボード監視は、次の条件を満たしたときに完了します。

1. スポーンされたすべてのエージェントが終端状態（completedまたはfailed-and-handled）に到達している
2. QAレビューサイクルがブロッキングな問題なく完了している
3. セッション状態が最終結果を反映している
4. 将来の参照用に結果がメモリへ記録されている

## 技術詳細

### ターミナルダッシュボード（oma dashboard terminal）

- **ファイル監視：** [chokidar](https://github.com/paulmillr/chokidar)を`awaitWriteFinish`（安定化しきい値200ms、ポーリング間隔50ms）付きで使い、書き込み途中のファイルを表示しないようにします。
- **レンダリング：** ファイル変更イベントのたびにターミナル全体を消去して再描画します。ANSIカラー出力には`picocolors`、枠線にはUnicodeの罫線文字を使います。
- **メモリディレクトリ：** `MEMORIES_DIR`が設定されていればそれを使います。そうでなければ`<project>/.agents/state/memories`を使います。`<project>`は`--project-root <path>`またはカレントディレクトリです。ディレクトリがない場合は空のディレクトリを作成します。
- **正常終了：** `SIGINT`と`SIGTERM`を捕捉してchokidarの監視を閉じ、正常に終了します。

### Webダッシュボード（oma dashboard web）

- **HTTPサーバー：** Node.jsの`createServer`で、`/`にHTMLページ、`/recap`にリキャップページ、`/api/state`にJSON状態、`/api/recap`にリキャップデータを提供します。サーバーは`127.0.0.1`にバインドします。
- **WebSocket：** `ws`ライブラリを使います。ループバックオリジンからの接続には、クエリ文字列にプロセストークンを含める必要があります。接続時にクライアントへ完全な状態を送り、その後は`{ type: "update", event, file, data }`メッセージとして更新を送ります。
- **ファイル監視：** ターミナルと同じchokidar設定を使います。ファイル変更で`broadcast()`を呼び出し、現在の状態を作成して接続済みのすべてのWebSocketクライアントへ送ります。
- **デバウンス：** 急速なファイル書き込み（複数エージェントが同時に進捗を書き込む場合など）によりクライアントへ大量の更新を送らないよう、更新を100msデバウンスします。
- **自動再接続：** WebSocket接続が切れると、ブラウザーのクライアントは指数バックオフ（初期1秒、倍率1.5、最大10秒）で再接続します。
- **ポート：** デフォルトは9847で、`DASHBOARD_PORT`環境変数で変更できます。APIリクエストは`X-OMA-Dashboard-Token`または`?token=...`を受け付けます。トークンがない、または無効な場合は`401`を返します。
- **状態の構築：** `buildFullState()`関数は、更新のたびにセッション情報、タスクボード、エージェントの状態、ターン数、アクティビティフィードを1つのJSONオブジェクトに集約します。
