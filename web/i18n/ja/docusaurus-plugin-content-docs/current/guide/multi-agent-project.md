# マルチエージェントプロジェクト

## マルチエージェント協調を使うタイミング

機能が複数のドメインにまたがる場合に使います。たとえば、バックエンドAPI、フロントエンドUI、データベーススキーマ、モバイルクライアント、QAレビューが必要な機能です。単一のエージェントではスコープ全体を処理できず、互いのファイルに干渉せずに各ドメインを並行して進める必要があります。

マルチエージェント協調が適しているのは、次のような場合です。

- タスクに2つ以上のドメイン（フロントエンド、バックエンド、モバイル、db、QA、debug、pm）が関わる
- ドメイン間にAPIコントラクトがある（たとえば、Webとモバイルの両方がRESTエンドポイントを利用する）
- 並列実行によって経過時間を短縮したい
- すべてのドメインの実装後にQAレビューが必要である

タスクが1つのドメインだけで完結する場合は、該当するエージェントを直接使ってください。

## 全体の流れ：/planから/reviewまで

推奨するマルチエージェントワークフローは、4段階のパイプラインに従います。

### Step 1：/planで要件とタスクを分解する

`/plan`ワークフローはインラインで実行され、サブエージェントをスポーンせずに構造化された計画を作成します。

```
/plan
```

実行される処理：

1. **要件収集**：PMエージェントが対象ユーザー、主要機能、制約、デプロイ先について質問します。
2. **技術的な実現可能性の分析**：設定されたコードインテリジェンスプロバイダーを使い、再利用できるコードとアーキテクチャパターンを既存のコードベースから調べます。ネイティブ検索は、プロジェクト外のパスまたは無視対象のパスにだけ使います。
3. **APIコントラクトの定義**：エンドポイントのコントラクト（メソッド、パス、リクエスト・レスポンスのスキーマ、認証、エラーレスポンス）を設計し、`.agents/results/api-contracts/`に保存します（実行アーティファクト）。コミットする仕様は`docs/plans/contracts/`に昇格させます。
4. **タスク分解**：担当エージェント、タイトル、受入基準、優先度（P0〜P3）、依存関係を含む実行可能なタスクに分けます。
5. **計画のユーザーレビュー**：計画全体を提示して確認を求めます。明示的な承認なしにはワークフローは進みません。
6. **計画の保存**：承認済みの計画を`.agents/results/plan-{sessionId}.json`に書き込み、概要をメモリに記録します。

出力された`.agents/results/plan-{sessionId}.json`は、`/work`と`/orchestrate`の両方への入力になります。

### Step 2：/workまたは/orchestrateで実行する

実行方法は2つあります。

| 項目 | /work | /orchestrate |
|:-------|:-----------|:-------------|
| **対話** | インタラクティブ（各段階でユーザーが確認） | 自動（完了まで実行） |
| **PM計画** | 組み込み（Step 2でPMエージェントを実行） | 計画があればロードし、なければインラインで作成 |
| **ユーザーのチェックポイント** | 計画レビュー後（Step 3） | インライン計画もファンアウト前にレビューゲートを通る |
| **永続モード** | あり（完了まで終了できない） | あり（完了まで終了できない） |
| **適した用途** | 初回利用、監督が必要な複雑なプロジェクト | 繰り返し実行、タスクが明確なプロジェクト |

#### /work：インタラクティブなマルチエージェントパイプライン

```
/work
```

1. ユーザーのリクエストを分析し、関係するドメインを特定します。
2. PMエージェントを実行してタスクを分解し、`plan-{sessionId}.json`を作成します。
3. 計画をユーザーに提示して確認を求めます。**確認されるまで停止します。**
4. 優先度ティアごとにエージェントをスポーンします。P0を先に実行し、同じ優先度のタスクは並列で実行します。
5. メモリファイルを使ってエージェントの進捗を監視します。
6. すべての成果物をQAエージェントがレビューします（OWASP Top 10、パフォーマンス、アクセシビリティ、コード品質）。
7. QAがCRITICALまたはHIGHの問題を見つけた場合は、担当エージェントをQAの指摘付きで再スポーンします。各問題について最大2回繰り返します。同じ問題が残る場合は**探索ループ**を起動し、2〜3個の代替アプローチを生成して、別々のワークスペースで同じ種類のエージェントに異なる仮説を与えてスポーンし、QAが採点して最善の結果を採用します。

#### /orchestrate：自動並列実行

```
/orchestrate
```

1. `.agents/results/plan-{sessionId}.json`をロードします。使用できる計画がなければ、`/plan`をインラインで実行して計画を作成します。
2. `session-YYYYMMDD-HHMMSS`形式のセッションIDでセッションを初期化します。
3. メモリディレクトリに`orchestrator-session.md`と`task-board.md`を作成します。
4. 優先度ティアごとにエージェントをスポーンし、それぞれにタスクの説明、APIコントラクト、コンテキストを渡します。
5. `progress-{agent}.md`ファイルをポーリングして進捗を監視します。
6. 各エージェントの完了を`verify.sh`で検証します。PASS（終了コード0）なら受け入れ、FAIL（終了コード1）ならエラーのコンテキスト付きで再スポーンします（最大2回）。失敗が続く場合は探索ループを起動します。
7. すべての`result-{agent}.md`を集め、最終レポートを作成します。

### Step 3：CLIレベルのエージェント管理にagent spawnを使う

`agent spawn`コマンドは、ワークフローが内部で呼び出す低レベルの仕組みです。直接使うこともできます。

```bash
oma agent spawn backend "Implement user auth API with JWT" session-20260324-143000 -w ./api
```

**すべてのフラグ：**

| フラグ | 説明 |
|:-----|:-----------|
| `--vendor <vendor>` | CLIベンダーの上書き（antigravity/claude/codex/cursor/opencode/qwen/grok/pi）。このスポーンのモデル解決を上書きします。 |
| `-w, --workspace <path>` | エージェントの作業ディレクトリ。省略時はモノレポ設定から自動検出します。 |
| `--task-id <id>` | スポーンをセッション計画のタスクに紐付けます。デフォルトはエージェントIDです。 |
| `--isolation worktree` | スポーン用のgit worktreeを作成します。デフォルトでは追加の分離を行いません。 |
| `--read-only` | 子エージェントを調査ツールだけに制限し、自動承認フラグを抑制します。 |

**ベンダー解決の順序**（最初に一致したものを使います）：

1. コマンドラインの`--vendor`フラグ
2. このエージェントに対する`oma-config.yaml`の`agents:`オーバーライド
3. アクティブな`model_preset`のエージェントデフォルト

設定の詳細は[エージェントごとのモデル](./per-agent-models.md)を参照してください。

**ワークスペース自動検出**では、次の順序でモノレポ設定を調べます。pnpm-workspace.yaml、package.jsonのworkspaces、lerna.json、nx.json、turbo.json、mise.toml。各ワークスペースディレクトリをエージェント種別のキーワード（frontendなら「web」「frontend」「client」など）で採点します。モノレポ設定がない場合は、`apps/web`、`apps/frontend`、`frontend/`などのハードコードされた候補にフォールバックします。

**プロンプトの解決**：`<prompt>`引数にはインラインテキストまたはファイルパスを指定できます。パスが既存ファイルに解決される場合は、その内容を読み込んでプロンプトとして使います。CLIは`.agents/skills/_shared/runtime/execution-protocols/{vendor}.md`からベンダー固有の実行プロトコルも注入します。

### Step 4：/reviewでQA検証を行う

```
/review
```

レビューのワークフローは、QAのフルパイプラインを実行します。

1. **スコープの特定**：何をレビューするか（特定のファイル、機能ブランチ、プロジェクト全体）を確認します。
2. **自動セキュリティチェック**：`npm audit`、`bandit`など同等のチェックを実行します。
3. **OWASP Top 10の手動レビュー**：インジェクション、認証の破綻、機密データ、アクセス制御、設定ミス、安全でないデシリアライゼーション、脆弱なコンポーネント、不十分なログを確認します。
4. **パフォーマンス分析**：N+1クエリ、インデックス不足、上限のないページネーション、メモリリーク、不要な再レンダリング、バンドルサイズを調べます。
5. **アクセシビリティ**：セマンティックHTML、ARIA、キーボード操作、色のコントラスト、フォーカス管理を含むWCAG 2.1 AAを確認します。
6. **コード品質**：命名、エラー処理、テストカバレッジ、TypeScript strictモード、未使用インポート、async/awaitのパターンを確認します。
7. **レポート**：CRITICAL / HIGH / MEDIUM / LOWに分類し、`file:line`、説明、修正コードを含めて報告します。

大きなスコープでは、ワークフローがQAエージェントのサブエージェントに委任します。`--fix`オプションを使うと修正と検証のループに入り、CRITICAL/HIGHの問題を修正するためにドメインエージェントをスポーンして再レビューし、最大3回繰り返します。

## セッションID戦略

すべてのオーケストレーションセッションには、次の形式の一意な識別子が付与されます。

```
session-YYYYMMDD-HHMMSS
```

例：`session-20260324-143052`

セッションIDは次の用途に使われます。

- メモリファイルの名前（`orchestrator-session.md`、`task-board.md`）
- システムの一時ディレクトリにあるPIDファイルでのエージェントプロセス追跡（`/tmp/subagent-{session-id}-{agent-id}.pid`）
- ログファイルの関連付け（`/tmp/subagent-{session-id}-{agent-id}.log`）
- `.agents/results/parallel-{timestamp}/`への結果のグループ化

セッションIDは`/orchestrate`のStep 2で生成され、すべてのスポーンされたエージェントに渡されます。これにより、1回の実行に属するエージェント、ログ、PIDを追跡できます。

## ドメインごとのワークスペース割り当て

各エージェントはファイル競合を防ぐため、分離されたワークスペースディレクトリでスポーンされます。割り当ては次のルールに従います。

### 自動検出

`-w`を省略するか`.`にすると、CLIは次の方法で最適なワークスペースを検出します。

1. モノレポ設定ファイル（pnpm-workspace.yaml、package.json、lerna.json、nx.json、turbo.json、mise.toml）を調べます。
2. `apps/*`などのglobパターンを実際のディレクトリに展開します。
3. エージェント種別のキーワードで各ディレクトリを採点します。

| エージェント種別 | キーワード（優先順） |
|:-----------|:---------------------------|
| frontend | web, frontend, client, ui, app, dashboard, admin, portal |
| backend | api, backend, server, service, gateway, core |
| mobile | mobile, ios, android, native, rn, expo |

4. ディレクトリ名が完全一致なら100点、キーワードを含むなら50点、パスに含むなら25点です。
5. 最も高いディレクトリを選びます。

### フォールバック候補

モノレポ設定がない場合は、次の候補を順番に確認します。

- **frontend：** `apps/web`、`apps/frontend`、`apps/client`、`packages/web`、`packages/frontend`、`frontend`、`web`、`client`
- **backend：** `apps/api`、`apps/backend`、`apps/server`、`packages/api`、`packages/backend`、`backend`、`api`、`server`
- **mobile：** `apps/mobile`、`apps/app`、`packages/mobile`、`mobile`、`app`

何も一致しない場合は、現在のディレクトリ（`.`）で実行します。

### 明示的なオーバーライド

常に使える指定：

```bash
oma agent spawn frontend "Build landing page" session-id -w ./packages/web-app
```

## コントラクトファーストルール

APIコントラクトはエージェント間の同期メカニズムです。コントラクトファーストルールの要点は次のとおりです。

1. **実装を始める前にコントラクトを定義します。** `/plan`ワークフローのStep 3でAPIコントラクトを作成し、`.agents/results/api-contracts/`（または永続仕様は`docs/plans/contracts/`）に保存します。
2. **各エージェントは関連するコントラクトをコンテキストとして受け取ります。** `/orchestrate`のStep 3でスポーンすると、各エージェントに「タスクの説明、APIコントラクト、関連コンテキスト」が渡されます。
3. **コントラクトがインターフェース境界を定義します。** コントラクトには次を定めます。
   - HTTPメソッドとパス
   - リクエストボディのスキーマ（型付き）
   - レスポンスボディのスキーマ（型付き）
   - 認証要件
   - エラーレスポンスの形式
4. **コントラクト違反を監視中に検出します。** `/work`のStep 5で、設定されたコードインテリジェンスプロバイダーを使い、エージェント間のAPIコントラクトの整合性を確認します。ネイティブ検索は、プロジェクト外のパスまたは無視対象のパスにだけ使います。
5. **QAレビューでコントラクトへの準拠を確認します。** QAエージェントのAlignment Review（ultraworkのStep 6）が実装を計画と照合します。APIコントラクトも対象です。

コントラクトがないと、バックエンドエージェントが`{ "user_id": 1 }`を返し、フロントエンドエージェントが`{ "userId": 1 }`を利用するような事態になります。コントラクトファーストルールは、この統合バグを防ぎます。

## マージゲート：4つの条件

マルチエージェント作業を完了とみなすには、次の4条件を満たす必要があります。

### 1. 宣言したチェックが成功する

すべての受入基準に関連するチェックがあり、計画で宣言したチェックが成功する必要があります。ビルドはタスクのプロジェクトゲートで必要な場合にのみ含め、結果コントラクトには実際に実行したコマンドと終了コードを記録します。

### 2. テストがパスする

既存のテストが引き続きパスし、新しいテストが実装した機能をカバーする必要があります。QAエージェントはコード品質レビューの一部としてテストカバレッジを確認します。

### 3. 計画したファイルだけが変更されている

エージェントは担当スコープ外のファイルを変更してはいけません。検証ステップで、エージェントのタスクに関係するファイルだけが変更されたことを確認します。これにより、意図しない副作用を防ぎます。

### 4. QAレビューで問題がない

QAエージェントのレビューでCRITICALまたはHIGHの指摘が残っていない必要があります。MEDIUMとLOWは今後のスプリント用に記録できますが、ブロッカーは解消してから進めます。

## スポーン例

### 単一エージェントのスポーン

```bash
# Spawn backend agent with Gemini (default)
oma agent spawn backend "Implement /api/users CRUD endpoint per API contract" session-20260324-143000

# Spawn frontend agent with Claude, explicit workspace
oma agent spawn frontend "Build user dashboard with React" session-20260324-143000 --vendor claude -w ./apps/web

# Spawn from a prompt file
oma agent spawn backend ./prompts/auth-api.md session-20260324-143000 -w ./api
```

### agent parallelによる並列実行

YAMLのタスクファイルを使う場合：

```yaml
# tasks.yaml
tasks:
  - agent: backend
    task: "Implement user authentication API with JWT tokens"
    workspace: ./api
  - agent: frontend
    task: "Build login page and auth flow UI"
    workspace: ./web
  - agent: mobile
    task: "Implement mobile auth screens with biometric support"
    workspace: ./mobile
```

```bash
oma agent parallel tasks.yaml
```

インラインモードを使う場合：

```bash
oma agent parallel --inline \
  "backend:Implement user auth API:./api" \
  "frontend:Build login page:./web" \
  "mobile:Implement auth screens:./mobile"
```

バックグラウンドモード（待機しない）：

```bash
oma agent parallel tasks.yaml --no-wait
# Returns immediately, results written to .agents/results/parallel-{timestamp}/
```

ベンダーを上書きする場合：

```bash
oma agent parallel tasks.yaml --vendor claude
```

## 避けるべきアンチパターン

### 1. 計画への形式的な同意

`/orchestrate`は、使える計画ファイルがない場合に`/plan`でインライン計画を作成できます。インライン計画も`/plan`のレビューゲートを通り、次のステップでその承認済みの分解に従ってファンアウトします。複数ドメインの大きな作業では、最初に`/plan`を実行して`docs/plans/work/`に永続的なトラッカーを作成し、エージェントのスポーン前に分解を調整できるようにします。

### 2. ワークスペースの重複

2つのエージェントを同じワークスペースディレクトリに割り当てることです。ファイル競合で一方の変更が他方を上書きします。常に別のワークスペースディレクトリを使います。

### 3. APIコントラクトの欠落

コントラクトを定義せずにバックエンドとフロントエンドのエージェントをスポーンすることです。データ形式、フィールド名、エラー処理について互換性のない前提を置くことになります。

### 4. QA指摘の無視

QAレビューを任意とみなすことです。CRITICALとHIGHの指摘は、本番で発生する実際のバグを表します。マージ前に解消してください。

### 5. 手動によるファイル調整

検証とQAのパイプラインに統合を任せず、エージェントの出力を手動でマージしようとすることです。自動パイプラインは手作業のレビューで見落とす問題を検出します。

### 6. 過剰な並列化

P0のタスクが完了する前にP1のタスクを実行することです。P1はP0の成果物に依存することが多いためです。ワークフローはティアの順序を自動で管理します。

### 7. 検証の省略

結果コントラクトを記録せずに`agent spawn`を直接使うことです。タスクで指定したチェックを実行して構造化されたclaimを完了させます。[エージェントの結果と再開](/docs/guide/agent-results-and-resume)を参照してください。ワークフローの検証ステップで、チェック失敗やスコープ逸脱を再利用前に検出します。

## ドメインをまたぐ統合の検証

すべてのエージェントが個別のタスクを終えたら、ドメイン間の統合を検証します。

1. **APIコントラクトの整合性**：設定されたコードインテリジェンスプロバイダーで、バックエンドの実装がフロントエンドとモバイルの利用するコントラクトに一致することを確認します。ネイティブ検索は、プロジェクト外のパスまたは無視対象のパスにだけ使います。
2. **型の一貫性**：複数ドメインで共有するTypeScript型、Pythonデータクラス、Dartモデルのフィールド名と型が一致する必要があります。
3. **認証フロー**：バックエンドがJWT認証を実装する場合、フロントエンドはヘッダーでトークンを正しく送信し、モバイルアプリはトークンを保存して更新する必要があります。
4. **エラー処理**：APIの利用者はすべて、文書化されたエラーレスポンスを処理する必要があります。バックエンドが`{ "error": "unauthorized", "code": 401 }`を返すなら、すべてのクライアントがこの形式を処理します。
5. **データベーススキーマの整合性**：データベースエージェントがマイグレーションを作成した場合、バックエンドのORMモデルはスキーマと正確に一致する必要があります。

QAエージェントのAlignment Review（ultraworkのStep 6、workのStep 6）がこのドメイン間検証を体系的に実行します。

## 完了時の条件

マルチエージェントプロジェクトは、次の条件を満たした時点で完了です。

- すべての優先度ティアの全エージェントが正常に完了している
- すべてのエージェントの検証スクリプトが終了コード0でパスしている
- QAレビューでCRITICALとHIGHがゼロである
- ドメイン間のAPIコントラクト整合性が確認されている
- ビルドが成功し、すべてのテストがパスしている
- 最終レポートがメモリに書き込まれ、ユーザーに提示されている
- ユーザーが最終承認している
