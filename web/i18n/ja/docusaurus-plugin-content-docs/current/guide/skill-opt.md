# スキル最適化

`oma skill optimize` は、`oma skill eval` が生成する `utilityLift` を最大化するよう `SKILL.md` を改善します。生のロールアウト証拠、スコープを持つ永続知識、実行可能なスキルを分けます。Wiki メンテナーが観測できる成功と失敗をまとめ、提案者がその知識から、追加・削除・置換の範囲を限定した編集を出力します。候補は、学習または検証の効用を改善する必要があります。どちらの分割も悪化させてはならず、タスクと負の転移の測定は完全でなければなりません。`--apply` には、完全に測定されて悪化のない、実行側が所有する最終テストと、検証済みのライブ隔離も必要です。デプロイ時に推論用の Wiki 検索は追加されず、出力は `SKILL.md` のままです。

研究上の根拠：Tang, L., Rashtchian, C., Ferng, C.-S., Tomkins, A., Juan, D.-C., & Vu, T. (2026). *WikiSkill: Compiling agent experience into persistent knowledge for skill evolution* [Preprint]. arXiv. https://doi.org/10.48550/arXiv.2608.27454

現在の CLI 最適化には `--live` が必要で、モデル呼び出しが発生します。デフォルト（非ライブ）の経路と `--mock` は、記録済みの提案を読み込むローダーが実装されていないため、提案を生成も再生もできず、評価の前に停止します。オフラインの再生には `oma skill eval --mock` を使ってください。注入するオプティマイザと採点器の API は、オフラインテスト用に引き続き利用できます。`--live` と `--mock` を両方指定するとエラーになります。

## 必須の依存関係：評価タスクのフィクスチャ

`oma skill optimize` は評価タスクのフィクスチャなしでは実行できません。`.agents/eval/<skill>/` に少なくとも **5 個のタスクフィクスチャ**（`MIN_TASKS = 5`）が必要です。5 個未満の場合、コマンドはすぐにエラーになります。

```
[oma skill opt] no eval coverage for skill "oma-scholar": found 2 task fixture(s), need at least 5. Author tasks first — see web/docs/guide/skill-eval.md
```

`.agents/eval/<skill>/` のディレクトリ規約、フィクスチャスキーマ、チェッカーの種類、モック再生用のロールアウトの準備については、[スキルユーティリティ評価ガイド](/docs/guide/skill-eval)を参照してください。

昇格には、他のスキルに属する同一ドメインの近隣タスクが、空でない集合として必要です。候補ごとの検証スコアと最終候補のスコアは、いずれも、評価した分割の近隣タスクを、候補本文そのものを使って測定している必要があります。近隣タスクがない場合や、ペアの記録が不完全な場合は、負の転移がないことを立証できません。オフライン評価で再生できるのは、一致する候補の記録だけです。新しい候補を生成して評価するには、ライブ最適化を使ってください。

再生とスイート単位の知識は、適用されるデフォルトの judge ルーブリックと採点器プロトコルのリビジョンを含む、タスクと評価器の契約全体に結び付いています。この出所情報のアップグレード以降は、古い記録と既存の知識スコープに新しい証拠が必要です。古いスコアに新しいハッシュを付け直しても、有効な測定にはなりません。

## 動作

フィクスチャはタスク ID で並べ替え、**学習（train）**、**検証用保留（held-out validation）**、**実行側が所有する最終テスト（runner-owned final-test）** に決定的に分割されます。5 個以上ある場合、目標比率は 60/20/20 で、各分割に少なくとも 1 タスクを入れます。たとえば、フィクスチャが 8 個の場合、丸め後は学習 4 個、検証 1 個、最終テスト 3 個のタスクになります。同じ `group` を宣言したフィクスチャはまとめて割り当てられるため、言い換えた兄弟タスクが学習に、元のタスクが最終テストに入ることはありません。グループが 3 つ未満の場合、分割はタスク ID にフォールバックし、警告を出します。最終テストのタスクはこのローカルフィクスチャセットから選ばれ、メンテナーと提案者からは隠されます。最終テストのタスク ID の重複や、開発用の分割との重なりは拒否されます。

各エポック（`--max-epochs` の上限、デフォルト 8）で次を行います。

1. **現在の最良の `SKILL.md` を学習分割で採点します。** `oma skill eval` が、タスクごとの観測可能なプロンプト、出力、改善幅を返します。内部分割のすべてのタスクで、両方の実験群が採点されている必要があります。失敗した比較や欠けた比較で分母を小さくすることはできません。
2. **Wiki メンテナーが証拠をまとめます。** 最大 5 件の失敗と 3 件の成功を、証拠と結び付いたパターンにします。失敗は学習価値で選びます。まず回帰、次に共通して最も根深い失敗の順に選び、両方の実験群がすでに合格しているタスクは、次の編集について何も示さないため除外します。成功は改善幅の順に並べます。スコープを持つパターンと過去のゲート結果は、OMA の L1/L2/L3 メモリシステムから再利用されます。
3. **提案者が K 個の候補編集を出力します。** 上限は `--edits-per-epoch` のデフォルト値である 4 件です。永続的な却下履歴にすでにある完全一致の編集はスキップします。
4. **各候補編集について：**
   - `SKILL.md` のメモリ内コピーに編集を適用します。
   - 候補を検証します（frontmatter の `name` と `description` は残り、本文はパースできなければなりません）。
   - 文章上の学習率予算を適用します。正味の文字変更が `--lr`（デフォルト 600）を超える編集を破棄します。
   - **検証用保留分割**のすべてのタスク（近隣タスクではベースラインと候補のペア比較を含む）と、**学習分割（held-in**）のすべてのタスク（近隣タスクの比較なし）で候補を再採点します。
5. **最良の有効な候補を受け入れます。** held-in/held-out のルールに従い、候補はどちらの分割でも何も失わず（`Δval ≥ 0` かつ `Δtrain ≥ 0`）、少なくとも一方で改善している必要があります。候補は `Δval + Δtrain` で順位付けします。検証での厳密な改善は必須ではありません。すべての検証タスクにすでに合格している本文でも、保留分割の成果を失わずに、学習での失敗を修復できるためです。その修復が一般化するかどうかは、最終テストが決めます。タスクのカバレッジは完全でなければなりません。空でない負の転移サンプルは、完全に測定されている必要があります。`NEG_TRANSFER_FAIL = -0.1` 以下の確認済みの回帰を示す近隣タスクがあってはなりません。ライブ実行では、最初のペア比較で回帰した近隣タスクを 1 回再測定します。記録される差分は 2 回の比較の平均で、再現された回帰（`confirmed: true`）だけが候補を却下します。モック再生は再測定できないため、1 回の試行での回帰がそのまま有効になります。ライブのレポートは `isolation: "enforced"` を宣言していなければなりません。提案ゲートの結果は、`deltaLift`（検証）、`deltaTrainLift`、判定の根拠となった近隣タスクの差分とともに記録されます。
6. 受け入れられた編集がないエポックが 2 回続いたら早期停止します（`OPT_EARLY_STOP_PATIENCE = 2`）。
7. **改善後に実行側が所有する最終テストを実行します。** 元の本文と検証の勝者の両方が、すべての最終テストのタスクをカバーしている必要があります。候補は最終テストの改善幅を失ってはならず（`candidateLift >= baselineLift`）、完全で候補固有の負の転移チェックにももう一度合格する必要があります。厳密な改善を求めないのは、受け入れの根拠になった改善がすでに開発用の分割で示されており、小さく固定されたテストで厳密な改善まで求めると、ほとんどの修復が昇格できなくなるためです。`finalTest.findings` には、元の本文と候補のタスクごとの改善幅が一覧されるため、失敗したテストが本物の回帰なのか、ノイズを含む 1 つのタスクによるものなのかを読み取れます。最終テストがない、不完全、または失敗の場合は、昇格できません。測定済みの最終テストの失敗は監査記録として残り、後の最適化に向けた却下の知識にはなりません。

ループ中の最適化は、メモリ内の候補コピーに対して行います。

測定されなかった候補は、`insufficient-coverage`、`negative-transfer-unmeasured`、`unverified-isolation` などの理由とともに `inconclusive` として記録されます。学習用の却下履歴からは除外され、評価条件が修復された後に再試行できます。確認済みの近隣タスクの回帰、どちらかの分割での悪化（`split-regression`）、どちらの分割でも改善がないこと（`no-validation-lift`）は却下になります。評価の不完全さや、メンテナーの劣化（`degraded`）を示す診断は、昇格をブロックします。

## 使い方

```
oma skill optimize --skill <id> --live
               [--dry-run | --apply]
               [--max-epochs <n>] [--edits-per-epoch <k>] [--lr <chars>]
               [--yes]
               [--json] [--output <format>]
```

### フラグ

| フラグ | デフォルト | 説明 |
|:-----|:--------|:-----------|
| `--skill <id>` | `_all` | 最適化するスキル ID（単純名。パス区切りなし）。 |
| `--dry-run` | **yes（デフォルト）** | `SKILL.md` を変更せずに編集案と diff を表示します。生成された証拠と進化イベントは保存されます。 |
| `--apply` | なし | すべての昇格ゲートに合格した、検証済みの候補を書き込みます。最終テストと負の転移の証拠が完全であることも含みます。アトミックな書き込み前に元ファイルをバックアップします。OMA 所有のスキルには `--yes` も必要です。 |
| `--mock` | 非ライブのデフォルト | CLI での提案の再生は実装されていないため、この経路は評価の前に停止します。オフラインの評価再生には `oma skill eval --mock` を使います。 |
| `--live` | なし | 現在の CLI 最適化に必須です。実際のモデル呼び出しが発生します。コストプレビューを表示し、`--yes` がなければ確認を求めます。 |
| `--max-epochs <n>` | `8` | 最大の最適化エポック数。 |
| `--edits-per-epoch <k>` | `4` | 1 エポックあたりに最適化 LLM が提案する候補編集数。 |
| `--lr <chars>` | `600` | 文章上の学習率予算。受け入れる編集 1 件あたりの正味文字変更上限。 |
| `--yes` | なし | ライブのコストプレビューの確認を省略します。OMA 所有のスキルへ適用する場合は、上書きの動作を承知したものとして扱います。 |
| `--json` | なし | CI/CD 用に JSON で出力します。 |
| `--output <format>` | `text` | 出力形式（`text` または `json`）。 |

## 最小のエンドツーエンド例

```bash
# Evaluate one epoch and print a candidate diff without applying it
oma skill optimize --skill oma-scholar --live --dry-run --max-epochs 1
```

8 個のフィクスチャと、すべての昇格ゲートに合格する候補を想定した出力例:

```
[oma skill opt] skill: oma-scholar, tasks: 8 (train: 4, val: 1, test: 3), dry-run: true

Skill opt  (skill: oma-scholar)
  applied: false
  baselineLift: 0.0%  finalLift: 100.0%  (train 50.0% → 100.0%)
  epochs: 1  acceptedEdits: 1  rejected: 0
  budget: 42 model calls used (no limit)
  finalTest: pass baseline=0.0000 candidate=0.3333

  diff:
--- a/SKILL.md
+++ b/SKILL.md
@@ -12,6 +12,9 @@
 ### When to use
 - User asks to look up an academic paper or technical claim.
+- User asks for a summary of arxiv abstracts or DOI-linked documents.
 - User wants citations or sources for a factual statement.
```

diff は最適化が書き込む内容を示します。`SKILL.md` は変更されませんが、生成された進化の証拠とスコープ付きゲート結果は今後の実行に向けて保存されます。

## 検証済みの改善を適用する

候補の diff を確認して問題がなければ、`--apply` で再実行します。

```bash
# Apply accepted edits (backs up the original first)
oma skill optimize --skill oma-scholar --live --apply --yes
```

### アーティファクトとしての手順

オプティマイザとメンテナーのプロンプトが、改善の手順そのものです。これらは組み込みのデフォルトとして提供され、`.agents/evolution/` 配下のファイルで上書きできます（ユーザー所有です。`.agents/eval/` とは異なり、インストールマニフェストによってコピーされることも、`oma update` によって削除されることもありません）。

| ファイル | 役割 | 必須のプレースホルダー |
|---|---|---|
| `optimizer.md` | 学習の証拠と永続知識から `SKILL.md` の編集を提案する | `{{body}}`、`{{findings}}`、`{{editsPerEpoch}}`（`{{knowledge}}` も） |
| `maintainer.md` | 証拠を再利用できるパターンにまとめる | `{{evidence}}`、`{{priorFacts}}`（`{{skillId}}`、`{{suiteHash}}`、`{{epoch}}` も） |
| `constitution.yaml` | ループが決して書き込んではならない領域、メタ最適化が変更してよい手順の部分、メタ実行用のデフォルトの正解 `anchors`、ディスパッチの予算を定める | 自分自身を `immutable` に列挙する必要がある |

`budget.max_dispatches_per_run`（デフォルトは `null`、無制限）は、ライブ実行で強制されます。基盤となるモデル呼び出し（タスクの実験群、近隣の実験群、judge、オプティマイザ、メンテナー）は 1 回ごとに 1 単位を消費し、上限を超える呼び出しは、実行される前に拒否されます。その後ループは `budget:exhausted` の診断とともに停止し、最終テストはスキップされ、昇格はブロックされ、結果には `budget: { limit, used }` が報告されます。上限の有無にかかわらず、使用量は実行サマリーに記録されるため、手順をコストと改善の両面で比較できます。

`oma skill procedure` は、有効なソースとそのハッシュを表示します。`--export` は、編集用にデフォルトを書き出し、既存のファイルは上書きしません。必須のプレースホルダーを欠いたテンプレートは、黙って機能を落として使われるのではなく、拒否されます。すべての実行は、結果、実行サマリー、昇格の系譜に `procedure`（部分ごとのハッシュと、結合したハッシュ）と `memory` を記録します。そのため、ある手順で得た証拠が別の手順のものと取り違えられることはありません。

オプティマイザの応答は、書式に限って寛容に読み取られます。コードフェンスと空行は無視されますが、有効な `EDIT:` 行（または単独の `NO_ACTION`）ではない内容行は `parse-error` になります。診断には最初の問題行も含まれるようになり、失敗の原因をたどれます。

### メモリのアブレーションと長期実行の統計

`--memory none` は、空の知識（想起されたパターンもゲート履歴もなし）から実行を開始しますが、実行の記録は残します。同じ予算で `--memory recall`（デフォルト）と `--memory none` の実行を比べることが、永続知識が役に立つかどうかの検証です。ループが経験から学ぶという主張に必要なのはこの比較であり、メモリが存在することではありません。

`oma skill evolution-stats --skill <id>` は、`.agents/results/skill-evolution/<id>/*.jsonl` にあるスキルの記録済みの実行をすべて集計します。内容は、ステータス別の実行数、ゲート結果別の提案数と受け入れ率、検証済みの改善（最終テストに合格し、昇格の資格がある）、適用とロールバック、最終改善幅の平均、計測された実行でのモデル呼び出し数と検証済みの改善 1 件あたりの呼び出し数（1 回の実行ではなく、プロセス全体のコスト）、そして同じ数値をメモリモード別と手順ハッシュ別に分けたものです。メタ最適化のレポートには、現在の手順と各候補について、内側の実行 1 回あたりの平均呼び出し数が表示されます。そのため、多くのコストをかけて改善幅で勝つ手順を、そうと見分けられます。

### メタ最適化：手順を候補にする

`oma skill meta-optimize --target optimizer --skill <a> <b> ... --live` は、オプティマイザ（またはメンテナー）のプロンプトを検証対象として扱います。名前を指定した保留スキルごとに、現在の手順で内側のループ（`oma skill optimize --dry-run`）を `--repeats` 回実行します。次に提案者へ、テンプレートに対する小さな編集を最大 `--candidates` 件求めます。各候補の手順でも、同じ `--max-epochs` と `--edits-per-epoch` の予算で内側のループをもう一度実行します。そして、内側のループが達成した学習の改善幅と検証の改善幅の合計について、各候補を現在の手順と（スキル、繰り返し）の組ごとにペア比較します。

候補が昇格するのは、改善幅の差のペア・ブートストラップ 95% 区間がゼロより上にあり（シード固定、1000 回の再標本化）、ペアが少なくとも 3 組あり、現在の手順で改善したスキルが、候補の手順でその改善の半分を超えて失うことがない場合だけです。評価がブロックされた内側の実行（カバレッジ不足、隔離の未検証、予算の枯渇）は失敗として報告され、ペアから除外されます。そのため、障害が一方の手順の改善ゼロとして数えられることはありません。保留スキルには伸びしろが必要です。現在の本文がすでに満点を取るスキルは、どの手順でも改善を示せません。`--anchor` は、選択には一切使わず、ドリフトを示すために現在の手順と勝者の手順で 1 回ずつ実行するスキルを指定します。このフラグがなければ constitution の `anchors` リストが適用されるため、一度宣言した正解データのセットは、すべてのメタ実行でチェックされます。`--apply` を付けると、勝者のテンプレートが `.agents/evolution/<target>.md` に書き込まれ、タイムスタンプ付きのバックアップ、unified diff 形式のパッチ、`.agents/results/skill-evolution/_procedure/promotions.jsonl` への記録が作られます。記録には、親と候補のハッシュ、constitution のハッシュ、根拠（スキル、繰り返し、予算、ペア、区間）が含まれます。`--apply` がなければ何も書き込まれません。

凍結されているものは次のとおりです。すべてのスキルの最終テスト分割は、選択のために読み取られることがありません（指標は学習と検証の改善幅の合計です）。評価器と最適化のコードは、constitution の `immutable` に列挙されています。constitution 自体は対象にできません。対象は `meta_targets` に含まれている必要があります。内側の実行は、デフォルトで `--memory none` を使います。手順を、以前の実行から想起した知識ではなく、手順自身が生み出す編集で評価するためです。同じ手順の内側の実行は、スキル間で並行して実行されますが（`OMA_META_CONCURRENCY`、デフォルトは最大 4）、1 つのスキルの繰り返しは直列のままです。各スキルの証拠が、それぞれ専用のアーティファクトファイルに書き込まれるためです。すべての内側の実行は、実行時の結合した手順ハッシュを記録するため、`oma skill evolution-stats` は後の結果を、それを生み出した手順に帰属させられます。

これは、自己改善システムのサーベイで説明されているレベル 5 の形です（Self-Harness の held-in/held-out 昇格、ブートストラップ区間を伴う ADAS の繰り返し評価、AlphaEvolve のような凍結された評価器）。手順はシステム自身が改訂しますが、外側の判定はループの手の届かない場所に置かれたままです。コストは、スキル数 × 繰り返し × (1 + 候補数) 回の内側の実行に比例して増えます。コマンドは上限を表示し、`--yes` がなければ確認を求めます。

### 昇格の系譜

`--apply` による書き込みは、そのたびに `.agents/results/skill-evolution/<skill>/promotions.jsonl` へ記録を追記し、その隣の `promotions/<candidate-hash>.patch` にレビュー可能な unified diff を書き出します。記録には、親と候補の本文ハッシュ、インストール先のパス、バックアップのパス、そして書き込みの根拠が含まれます。根拠は、検証と最終テストの改善幅、昇格の判定、フィクスチャスイートのハッシュ、評価器のプロトコルリビジョン、元と対象のランタイムです。`oma skill promotions --skill <id>` で、このログを一覧できます。

`oma skill rollback --skill <id>` は、直近の適用が置き換えた本文を復元します。インストール済みのファイルがその適用の候補と一致しなくなっている場合（後の手編集が破棄されてしまうため）、バックアップが記録された親と一致しない場合、またはその適用がすでにロールバック済みの場合は拒否します。ロールバックに成功すると、適用を指す `reverses` を付けて同じログに追記されます。OMA 所有のスキルでは、`oma update` がインストール済みのコピーを上書きするため、パッチをソースリポジトリやユーザーのオーバーレイに持ち込むアーティファクトとして使います。記録には `omaOwned: true` が付くため、後の更新が回帰と取り違えられることはありません。

`--apply` には、検証で悪化がない受け入れ済みの編集が 1 つ以上あること、`finalTest.passed: true`、`promotion.eligible: true` が必要です。これらのゲートでは、内部のタスクカバレッジが完全であること、空でなく完全に測定された候補固有の負の転移サンプルがあること、ライブの隔離が強制されていることが求められます。最終テストがない、測定が不完全、またはコンパイラの診断が劣化している場合、書き込みは行われません。アトミックな書き込みの前に元の `SKILL.md` のバックアップが作成され、レビュー用に diff が表示されます。

ライブ評価は、保護された Claude またはネイティブ Codex のプロファイルを通じて、隔離ゲートを満たせます。Claude は HOME と対象のチェックを維持します。Codex は、プロンプトを送る前に、一時的な app-server スレッドに指示のソースもツール環境もないことを検証します。他のランタイムプロファイルは探索用のままです。

### 進化した内容の確認

ループは 3 か所で自身の変化を知らせます。どれも、主張ではなく、追記専用の系譜ログから読み取った内容です。

- `oma skill promotions --all` は、すべてのスキルと手順にわたる変更ごとに 1 文を出力します。何を編集したか（受け入れた編集のアンカーと置換内容）、変更前後の held-in と held-out の改善幅、最終テストが通ったか、手順の昇格ではペアの改善幅の差、その区間、測定に使ったスキルです。`--skill <id>` を付けると 1 つのスキルに絞り込めます。このバージョンが書いた適用記録には、受け入れた編集と学習の改善幅が含まれます。古い記録はハッシュ表示にフォールバックします。
- `oma doctor` は **Evolution** の注記を表示します。適用およびロールバックされたスキル編集、スキルごとの最新の変更、手順の昇格、フィードバックを待っているもの（フィクスチャのないキャプチャ済みインシデント、まだキャプチャされていない失敗実行）と、それらを処理するコマンドです。
- セッションの開始時に、状態スナップショットのフックが `harness evolved since your last session` ブロックを注入します。これは、最後にこのブロックを表示したセッション以降に記録された昇格を一覧にしたもので、各変更は 1 回だけ通知されます。マーカーは `.agents/state/evolution-notice.json` にあります。

予算付きのフィードバックサイクルをスケジュール実行するには、[プロジェクトハーネス進化](./harness-evolution.md)を有効化します。

```bash
oma harness evolution enable --max-dispatches 300
oma harness evolution status --json
```

自動サイクルは、合格した変更をプロジェクトのオーバーレイとして適用し、未完了の作業は再試行のために保持し、サイクル全体で 1 つのディスパッチ上限を共有します。デフォルトのスケジュールは毎日ローカル時刻 03:00 です。適用せずに評価だけ実行するには `--mode propose` を、スケジュールを止めるには `oma harness evolution disable` を使います。手順のメタ最適化は、引き続き別の手動コマンドです。

## ライブモード

ライブモードは実際のメンテナーと提案者を呼び出し、エポックごとに評価の実験群をライブで再実行します。コストが高くなります。採点するタスクごとにベースラインと処置群の呼び出しがあり、判定フィクスチャが追加の採点呼び出しを行い、最終テストでは元の本文と候補本文を採点します。プレビューには、実際の分割から計算した上限が表示されます。内訳は、最初の検証ベースライン、学習とコンパイラの呼び出し、候補の検証呼び出し、2 回の最終テスト採点、そしてすべての候補と最終候補に対するペアの近隣チェックです。各呼び出しのタイムアウトは 120 秒です。保護された Claude と Codex の実験群は、ツール、指示の自動検出、MCP、最適化メモリを無効にします。

```bash
# Cost preview + confirm
oma skill optimize --skill oma-scholar --live

# Skip confirmation
oma skill optimize --skill oma-scholar --live --yes

# Live opt, then apply if improved
oma skill optimize --skill oma-scholar --live --apply --yes
```

コストプレビューには、LLM 呼び出しを始める前に基礎モデルの呼び出し上限が表示されます。

メンテナー、提案者、評価の実験群、judge は、新しい一時ディレクトリの中で、保護されたテキストトランスポートを共有します。Claude は制限付きの CLI プロファイルを使います。Codex はネイティブの `codex app-server` を使い、既存の CLI ログイン、選択したモデルとプロバイダー、推論の effort を引き継ぎます。API キーのクライアントに置き換えることも、Claude にフォールバックすることもありません。Codex プロファイルは、macOS/Linux 上の CLI 0.154.x で、ネイティブのファイル認証情報ストレージと既存の `auth.json` を使う構成を対象とします。各呼び出しは、認証情報の内容をコピーせずに元の設定ファイルと認証ファイルを参照する、専用の一時的な `CODEX_HOME` を用意します。ネイティブのトークン更新は、引き続き元の認証ファイルを使います。共有のブートストラップ状態は除外され、一時的な状態は後で削除されます。keyring、auto、ephemeral の認証情報ストアは、現時点では未対応です。スレッドの契約はモデルへの入力を送る前に検査され、未対応のバージョン、ストレージモード、プロトコルの失敗はディスパッチを終了させます。ツール、起動時の指示の検出、MCP アクセス、セッションの永続化は無効になっており、コンパイラのプロセスがエージェントツールを通じて、伏せられているフィクスチャを読めないようにしています。他のコンパイラのベンダーは、検証済みのトランスポートを持つまで、明示的に失敗します。

オプティマイザは、有効な編集には `proposed` を、明示的な `NO_ACTION` 応答にだけ `no-action` を報告します。プロセスや API の失敗は `dispatch-error` に、有効な編集を含まない不正な応答は `parse-error` になります。これらのエラーが空の編集リストになることはありません。メンテナーが検証済みのパターンを提供できない場合は、ディスパッチまたはパースの理由とともに `degraded` を報告します。フォールバックのパターンは永続知識から除外され、その実行で候補を昇格することはできません。評価の失敗は、学習用の却下履歴ではなく、`diagnostics` と提案ゲートの記録に現れます。

## JSON 出力

```bash
oma skill optimize --skill oma-scholar --live --dry-run --max-epochs 1 --json
```

```json
{
  "ok": true,
  "skill": "oma-scholar",
  "baselineLift": 0.0,
  "finalLift": 1.0,
  "baselineTrainLift": 0.5,
  "finalTrainLift": 1.0,
  "epochCount": 1,
  "acceptedEdits": [
    { "op": "add", "anchor": "### When to use", "after": "\n- User asks for a summary of arxiv abstracts or DOI-linked documents." }
  ],
  "rejectedCount": 0,
  "applied": false,
  "diff": "--- a/SKILL.md\n+++ b/SKILL.md\n...",
  "_dryRun": true,
  "finalTest": {
    "baselineLift": 0.0,
    "candidateLift": 0.3333,
    "passed": true,
    "findings": [
      { "taskId": "oma-scholar-doi-summary", "original": 0, "candidate": 1 },
      { "taskId": "oma-scholar-citation-format", "original": 0, "candidate": 0 },
      { "taskId": "oma-scholar-claim-check", "original": 0, "candidate": 0 }
    ]
  },
  "promotion": { "eligible": true, "reasons": [] },
  "diagnostics": [],
  "budget": { "limit": null, "used": 42 },
  "_split": { "trainCount": 4, "valCount": 1, "testCount": 3 }
}
```

`ok` には、`(applied || (acceptedEdits.length > 0 && finalLift >= baselineLift))`、`finalTest.passed === true`、`promotion.eligible === true` のすべてが必要です。`baselineTrainLift` と `finalTrainLift` は、検証の改善幅と並べて、held-in 分割の改善幅を報告します。`--apply` も同じ条件でゲートされます。学習での修復だけを理由に受け入れた編集は、最終テストにも合格した場合にだけ書き込まれます。最終テストや昇格オブジェクトがなければ `ok: true` にはなりません。`_split` のカウントは、使用されたローカルフィクスチャ分割の実数を示します。

たとえば、測定されなかった候補は、次のようなレポートの抜粋になることがあります。

```json
{
  "ok": false,
  "acceptedEdits": [],
  "rejectedCount": 0,
  "finalTest": { "baselineLift": 0.0, "candidateLift": 0.0, "passed": false },
  "promotion": {
    "eligible": false,
    "reasons": ["validation:inconclusive", "final-test-failed", "no-validated-candidate"]
  },
  "diagnostics": [
    {
      "stage": "validation",
      "status": "inconclusive",
      "message": "Candidate evaluation is incomplete; retry after repairing the evaluation conditions."
    }
  ]
}
```

再試行する前に、`diagnostics`、`promotion.reasons`、`finalTest.blocker` があればそれも確認してください。結論の出なかった（`inconclusive`）提案では `rejectedCount` は増えません。測定済みの最終テストの失敗は、その実行の監査用の却下数を増やすことがありますが、永続的な却下の知識からは除外されたままです。

## `oma-*` スキルの SSOT に関する注意

ID が `oma-` で始まるスキルは oh-my-agent が所有し、`oma update` で上書きされます。これらのスキルでは `--apply` は推奨しません。デフォルトの `--dry-run` を使い、意味のある改善ならレジストリへ反映してください。ユーザーが作成したスキルでは `--apply` を安全に使えます。

OMA 所有のスキルを対象にすると、コマンドは次の警告を表示します。

```
[oma skill opt] warning: "oma-scholar" is an oma-owned skill. --apply output will be overwritten by oma update. Consider using --dry-run and upstreaming the diff instead.
```

## 過学習ガード

メンテナーと提案者が受け取るのは TRAIN のロールアウト証拠です。候補の選択には保持した VALIDATION 分割を使い、実行側が別の TEST 分割を所有します。ツールを使わないコンパイラの実行により、伏せられているそれらのフィクスチャと評価器に、ワークスペースからアクセスすることはできません。

最終テストが失敗すると適用できません。その結果は監査用に残りますが、最終テストのゲート結果も、結論の出なかった提案も、永続的な最適化の知識にはなりません。記録処理、履歴の再読み込み、セマンティック想起の各経路も、レガシーの最終テスト結果を除外するため、後の実行が以前の最終テストの成功や失敗を学習フィードバックとして使うことはできません。

## CI への統合

既存の候補固有の記録をオフラインの CI でチェックするには、評価の再生を使います。

```bash
oma skill eval --skill oma-scholar --mock --neg-transfer --require-coverage --json
```

CLI の最適化自体には `--live` が必要です。記録済みの提案を再生するアダプターはまだありません。`oma skill optimize --mock` を完全なオフラインのオプティマイザとして説明していた以前の案内は誤りでした。オフラインの再生ジョブは `oma skill eval --mock` に移すか、ライブ最適化とそのモデルコストを明示的に有効にしてください。最適化の実行では、JSON の `ok` と `promotion.eligible` を確認してください。昇格できる候補が見つからなかった完了済みの実行も、終了コードは 0 になります。

最適化の終了コード：
- `0` の場合は、改善の有無にかかわらず最適化が完了しています。
- `1` の場合は、入力が無効、または実行に失敗しています。非ライブの CLI 最適化、`--live` と `--mock` の同時指定、フィクスチャ数の不足、未対応のコンパイラベンダー、オプティマイザのディスパッチ失敗、不正なオプティマイザ出力が含まれます。
