# バグ修正

## デバッグワークフローを使うタイミング

特定のバグを診断して修正するときは、自然言語で「fix bug」「fix error」「debug」と言うか、`/debug`を使います。このワークフローは、症状だけを修正して根本原因を残すというよくある問題を避ける、構造化された再現可能なデバッグ手順を提供します。

デバッグワークフローは設定されているすべてのベンダーに対応します。Step 1〜5はインラインで実行します。Step 6（類似パターンのスキャン）は、スキャン範囲が広い場合（10ファイル以上、または複数ドメインにまたがるエラー）に`debug-investigator`サブエージェントへ委任できます。その後、Step 7でメモリに記録します。

---

## バグレポートテンプレート

バグを報告するときは、次の情報をできるだけ多く提供します。各フィールドがデバッグワークフローの検索範囲を狭めます。

### 必須フィールド

| フィールド | 説明 | 例 |
|:------|:-----------|:--------|
| **エラーメッセージ** | 正確なエラーテキストまたはスタックトレース | `TypeError: Cannot read properties of undefined (reading 'id')` |
| **再現手順** | バグを引き起こす順序付きの操作 | 1. 管理者でログインする。2. /usersに移動する。3. 任意のユーザーの「Delete」をクリックする。 |
| **期待される動作** | 本来起こるべきこと | ユーザーが削除され、リストから消える。 |
| **実際の動作** | 実際に起こること | ページが白い画面でクラッシュする。 |

### 任意のフィールド（強く推奨）

<!-- oma-docs:ignore-start -->
| フィールド | 説明 | 例 |
|:------|:-----------|:--------|
| **環境** | ブラウザー、OS、Nodeのバージョン、デバイス | Chrome 124、macOS 15.3、Node 22.1 |
| **発生頻度** | 常に、ときどき、初回のみ | 常に再現する |
| **最近の変更** | バグが発生する前に変更されたもの | PR #142（ユーザー削除機能）をマージした |
| **関連コード** | 原因と疑っているファイルまたは関数 | `src/api/users.ts`、`deleteUser()` |
| **ログ** | サーバーログ、コンソール出力 | `[ERROR] UserService.delete: user.organizationId is undefined` |
| **スクリーンショット/録画** | 視覚的な証拠 | エラー画面のスクリーンショット |
<!-- oma-docs:ignore-end -->

最初に多くのコンテキストを提供するほど、デバッグワークフローが追加で質問する回数を減らせます。

## 重要度のトリアージ（P0〜P3）

重要度によって、バグの扱いと修正までの速さが決まります。

### P0：クリティカル（即時対応）

**定義：** 本番環境が停止している、データが失われているまたは破損している、セキュリティ侵害が進行している。

**対応の目安：** すべてを中断します。解決するまでこのタスクだけに対応します。

**例：**
- 認証システムが迂回され、すべてのユーザーが管理者エンドポイントにアクセスできる
- データベースマイグレーションでusersテーブルが破損し、アカウントにアクセスできない
- 決済処理で顧客に二重請求している
- APIエンドポイントが他のユーザーの個人データを返している

**デバッグ方法：** 完全なテンプレートを省略します。エラーメッセージとスタックトレースがあれば、ワークフローはStep 2（再現）から直ちに開始します。

### P1：高（同じセッション内）

**定義：** 主要機能が多数のユーザーに対して壊れている。回避策があっても、長期的には受け入れられない。

**対応の目安：** 現在の作業セッション内に修正します。解決するまで新機能の作業を始めません。

**例：**
- 特殊文字を含むクエリで検索結果が返らない
- 5MBを超えるファイルのアップロードに失敗する（上限は50MBの想定）
- Android 14のデバイスでモバイルアプリが起動時にクラッシュする
- パスワードリセットメールが送信されない（メールサービス統合が壊れている）

**デバッグ方法：** 7段階のループ全体を実行します。修正後にQAレビューを推奨します。

### P2：中（このスプリント）

**定義：** 機能は動作するが、挙動が劣化している。使いやすさに影響するが、機能自体は失われていない。

**対応の目安：** 現在のスプリントに予定し、次のリリース前に修正します。

**例：**
- テーブルの並べ替えが大文字と小文字を区別する（「apple」が「Zebra」の後に並ぶ）
- 設定パネルのダークモードでテキストが読みにくい
- /usersエンドポイントのAPIレスポンスタイムが8秒かかる（1秒未満であるべき）
- リストが空のときにページネーションが「Page 1 of 0」と表示する

**デバッグ方法：** 7段階のループ全体を実行し、QAの回帰テストスイートに含めます。

### P3：低（バックログ）

**定義：** 見た目の問題、エッジケース、軽微な不便。

**対応の目安：** バックログに追加します。都合のよいときに修正するか、関連する変更とまとめます。

**例：**
- ツールチップに「Delete」ではなく「Delet」と表示される誤字
- 非推奨のReactライフサイクルメソッドに関するコンソール警告
- ビューポート幅が768〜800pxの範囲でフッターの位置が2ピクセルずれる
- コンテンツが表示された後もローディングスピナーが200ms続く

**デバッグ方法：** 7段階のループ全体は不要な場合があります。回帰テストを伴う直接修正で十分です。

## 7段階デバッグループの詳細

`/debug`ワークフローは、次の段階を順に実行します。設定されたコードインテリジェンスプロバイダーを使います。ネイティブ検索は、プロバイダーが利用できないかタイムアウトした場合に、プロジェクト外のパスまたは無視対象のパスにだけ使います。

### Step 1：エラー情報を収集する

ワークフローは、次の情報をユーザーに尋ねるか、提供された情報から受け取ります。

- エラーメッセージとスタックトレース
- 再現手順
- 期待される動作と実際の動作
- 環境の詳細

プロンプトにエラーメッセージがすでに含まれている場合は、すぐにStep 2へ進みます。

### Step 2：バグを再現する

**使用するツール：** 設定された検索・シンボルツール。利用できない場合はネイティブの`rg`とスコープ付き読み取りを使います。

目的は、コードベース内でエラーの位置を特定することです。例外がスローされる正確な行、誤った出力を生成する正確な関数、予期しない挙動を引き起こす正確な条件を見つけます。

この段階で、ユーザーが報告した症状（「ページがクラッシュする」）をコードベース上の位置（`src/api/users.ts:47, deleteUser() throws TypeError`）に変換します。

### Step 3：根本原因を診断する

**使用するツール：** 利用できる場合は参照とシンボルのナビゲーションを使い、利用できない場合は対象を絞ったネイティブ読み取りを使います。

ワークフローはエラー位置から逆向きに追跡し、実際の原因を探します。次の一般的な根本原因パターンを確認します。

| パターン | 確認すること |
|:--------|:----------------|
| **Null/undefinedアクセス** | nullチェックの欠落、必要なオプショナルチェーン、初期化されていない変数 |
| **競合状態** | 非同期処理の完了順序が逆になる、awaitの欠落、共有可変状態 |
| **エラーハンドリングの欠落** | try/catchがない、Promiseの拒否が未処理、エラーバウンダリーがない |
| **誤ったデータ型** | 数値が必要な箇所に文字列がある、型変換の欠落、スキーマが正しくない |
| **古い状態** | Reactの状態が更新されない、キャッシュが無効化されない、クロージャが古い値を捕捉する |
| **バリデーションの欠落** | ユーザー入力がサニタイズされない、APIリクエストボディが検証されない、境界条件が未確認 |

症状ではなく根本原因を診断します。`user.id`がundefinedなら、その場所でユーザーがundefinedになる理由を調べます。undefinedを防ぐガードを追加する方法だけを考えてはいけません。

### Step 4：最小修正を提案する

ワークフローは次の内容を提示します。

1. コードの追跡結果を根拠にした、特定された根本原因
2. 必要な箇所だけを変更する修正案
3. 症状だけでなく根本原因を修正できる理由

このワークフローは、リクエストまたは実行ポリシーによって変更がすでに許可されていない場合、編集前に提案を示して確認を待ちます。許可済みであれば、追加の確認なしで続行します。

**最小修正の原則：** 変更する行を最小限にします。リファクタリング、コードスタイルの改善、無関係な機能の追加は行いません。修正は2分以内にレビューできる範囲にします。

### Step 5：修正を適用して回帰テストを書く

この段階では、次の2つを行います。

1. **修正を実装する：** 承認された最小限の変更を適用します。
2. **回帰テストを書く：** 次の条件を満たすテストを作成します。
   - 元のバグを再現する（修正なしではテストが失敗する）
   - 修正が機能することを確認する（修正ありではテストがパスする）
   - 将来の変更で同じバグが再発することを防ぐ

回帰テストは、デバッグワークフローの最も重要な成果物です。回帰テストがなければ、将来の変更で同じバグが再び混入します。

### Step 6：類似パターンをスキャンする

修正を適用した後、ワークフローはバグの原因になったパターンをコードベース全体から検索します。

**使用するツール：** 設定されたパターン検索、または根本原因として特定したパターンを使ったスコープ付きのネイティブ検索。

たとえば、`user.organization.id`へのアクセス時に`organization`がnullか確認していなかったことがバグの原因なら、nullチェックなしで`organization.id`にアクセスしている他の箇所をすべて探します。

**サブエージェント委任の基準：** 次の場合に`debug-investigator`サブエージェントをスポーンします。

- エラーが複数のドメインにまたがる（フロントエンドとバックエンドの両方に影響するなど）
- 類似パターンのスキャン範囲が10ファイル以上に及ぶ
- 完全な診断に深い依存関係の追跡が必要

ベンダーごとのスポーン方法：

| ベンダー | スポーン方法 |
|:-------|:------------|
| Claude Code | `.claude/agents/debug-investigator.md`を使うAgentツール |
| Codex CLI | モデルが仲介するサブエージェントリクエスト、結果はJSON |
| Gemini CLI | `oma agent spawn debug "scan prompt" {session_id} -w {workspace}` |
| Antigravity / フォールバック | `oma agent spawn debug "scan prompt" {session_id} -w {workspace}` |

脆弱性のある場所をすべて報告します。確認済みの箇所は同じセッションで修正します。

### Step 7：バグを文書化する

ワークフローは、次の内容をメモリファイルに書き込みます。

- 症状と根本原因
- 適用した修正と変更ファイル
- 回帰テストの場所
- コードベース全体で見つかった類似パターン

## /debugのプロンプトテンプレート

デバッグワークフローを起動するときは、構造化されたプロンプトを指定できます。

```
/debug

Error: TypeError: Cannot read properties of undefined (reading 'id')
Stack trace:
  at deleteUser (src/api/users.ts:47:23)
  at handleDelete (src/routes/users.ts:112:5)

Steps to reproduce:
1. Log in as admin
2. Navigate to /users
3. Click "Delete" on a user whose organization was deleted

Expected: User is deleted
Actual: 500 Internal Server Error

Environment: Node 22.1, PostgreSQL 16
```

**この構造が効果的な理由：**

- **エラーとスタックトレース**があれば、Step 2でコード内の位置をすぐに特定できます（`search_for_pattern`で「deleteUser」を検索して関数を見つけ、`find_symbol`で正確な場所を特定します）。
- **再現手順**に具体的なトリガー条件（「組織が削除されたユーザー」）を含めると、根本原因（nullの外部キー）の手がかりになります。
- **環境**によってバージョン固有の見当違いの原因を排除できます。

より単純なバグには、短いプロンプトでも十分です。

```
/debug The login page shows "Invalid credentials" even with correct password
```

ワークフローは必要に応じて追加の詳細を質問します。

## エスカレーションシグナル

次のシグナルは、標準のデバッグループを超えたエスカレーションが必要なことを示します。

### シグナル1：同じ修正を2回試した

ワークフローが修正を提案して適用した後も同じエラーが再発する場合、初期診断より深い問題があります。原因を再評価してください。試す価値のある代替案があり、既存の復旧予算で足りる場合は、実行中のワークフロー（ultrawork、orchestrate、work）の**探索ループ**を使います。

- 根本原因について2〜3個の代替仮説を作成する
- 各実験を分離し、そのベースライン、証拠、無関係な作業を保全する
- 必須の動作と比較可能な計測基準を満たすアプローチを選び、統合した結果を検証する

### シグナル2：複数ドメインにまたがる根本原因

フロントエンドのエラーが、バックエンドの変更によって発生し、その変更がデータベーススキーマのマイグレーションに起因している場合です。根本原因がドメイン境界をまたぐときは、関係するドメインエージェントを参加させるために`/work`または`/orchestrate`へエスカレーションします。

**例：** フロントエンドがユーザー名に「undefined」と表示する。バックエンドが`user.display_name`にnullを返す。データベースマイグレーションで列が追加されたが、既存行の値がNULLである。修正には、データベースのマイグレーション（バックフィル）、バックエンドのnull処理、フロントエンドのフォールバック表示が必要です。

### シグナル3：再現環境がない

バグが本番でしか発生せず、ローカルでは再現できない場合です。次のような兆候があります。

- 環境固有の設定差異
- 本番負荷でのみ発生する競合状態
- ステージングと本番で異なるサードパーティサービスの挙動

**対応：** 本番ログを収集し、本番監視へのアクセスを依頼します。修正を試す前に、インストルメンテーションまたはログを追加することも検討します。

### シグナル4：テストインフラストラクチャの障害

回帰テストを書けないほど、テストインフラストラクチャが壊れている、存在しない、または不十分な場合です。

**対応：** まずテストインフラストラクチャを修正するか、`oma install`で設定します。その後、デバッグワークフローに戻ります。実行可能なチェックが適用できない場合は、理由を結果コントラクトに記録し、合格したように見せるチェックを作らないでください。

## 修正後の検証チェックリスト

修正と回帰テストを適用した後、次を確認します。

- [ ] **回帰テストが修正なしでは失敗する**：一時的に修正を戻し、テストがバグを検出することを確認する
- [ ] **回帰テストが修正ありではパスする**：修正を適用し、テストがパスすることを確認する
- [ ] **関連する既存チェックが引き続きパスする**：変更した挙動を対象とするプロジェクトのチェックを実行する。ビルドはタスクが明示的に要求する場合にのみ実行する
- [ ] **類似パターンをスキャン済み**：Step 6を完了し、見つかった箇所をすべて修正または記録している
- [ ] **修正が最小限である**：必要な行だけを変更し、無関係なリファクタリングを含めていない
- [ ] **根本原因を文書化している**：メモリファイルに症状、根本原因、適用した修正、変更ファイル、回帰テストの場所、類似パターンを記録している

## 完了条件

デバッグワークフローは、次の条件を満たしたときに完了します。

1. 根本原因が特定され、文書化されている（症状だけではない）
2. タスクの承認範囲内で最小限の修正が適用されている
3. 修正なしでは失敗し、修正ありではパスする回帰テストがある
4. コードベース全体で類似パターンをスキャンし、確認済みの箇所をすべて対応している
5. 症状、根本原因、適用した修正、変更ファイル、回帰テストの場所、類似パターンを含むバグレポートがメモリに記録されている
6. 修正後も既存のすべてのテストがパスしている
