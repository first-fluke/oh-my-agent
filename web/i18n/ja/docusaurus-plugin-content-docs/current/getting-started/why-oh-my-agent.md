# oh-my-agent を選ぶ理由

oh-my-agent は、チームがすでに使っているエージェント CLI の周囲に、リポジトリで管理する層を追加します。`.agents/` ディレクトリには[スキル](./glossary.md#skill)、[ワークフロー](./glossary.md#workflow)、[エージェント定義](./glossary.md#agent-definition)、ルール、モデル設定を保存します。ベンダー固有のファイルはこの[信頼できるソース](./glossary.md#ssot)から生成されるため、プロジェクトと一緒に挙動をレビューして変更できます。

## リポジトリに調整レイヤーが必要なときに選ぶ

次のいずれかが必要なら、OMA が適しています。

- **複数のエージェントホストまたはベンダー。** `model_preset: auto` は現在のランタイムのネイティブ設定を使います。固定プリセットとカスタムプリセットでは、別のベンダーにロールを割り当てられます。ネイティブに処理しないロールは `oma agent spawn` がディスパッチします。
- **繰り返し使えるチームワークフロー。** `/work` は範囲を限定した1つのタスクを処理し、`/orchestrate` は委任した作業を調整し、`/ultrawork` はレビュー手順を含む並列作業を実行し、`/ralph` は明示的な judge フェーズ付きでタスクを繰り返します。
- **リポジトリで管理する指示。** スキル、ワークフロー、ルール、エージェント定義をコードのそばに置きます。`oma link` は選択したファイルをサポート対象ベンダーの形式に変換します。
- **機械的なチェックと保存される結果。** エージェントの実行では、構造化された状態と結果の実行記録を書けます。`oma verify agent <agent-type>` と `oma docs verify` を明示的に実行してチェックできます。

1つのホストだけを使い、共有スキル、ワークフロー、ベンダールーティングも必要としないプロジェクトでは、追加の `.agents/` ファイルと CLI コマンドが設定に見合わない場合があります。OMA は調整レイヤーです。ホストのモデルやエディター、プロジェクト固有の受入基準を置き換えるものではありません。

## 検証は必要なときに選んで実行する

バックエンド、フロントエンド、モバイル、QA、デバッグ、計画のロールに対するチェックを実行するときは、`oma verify agent <agent-type> --workspace <path>` を使います。検証器は静的検査と、テスト、型チェック、SQL チェック、`flutter analyze` など設定済みのコマンドを組み合わせます。詳しくは [`cli/commands/verify/report.ts`](https://github.com/first-fluke/oh-my-agent/blob/main/cli/commands/verify/report.ts) を参照してください。レポートには各チェックの結果が表示されます。チェックに合格しても、機能がプロダクト要件やドメイン要件を満たすことまでは証明しません。タスクの受入基準も確認してください。

`/ralph` を選んだ場合は、[judge](./glossary.md#judge) フェーズが別途追加されます。このフェーズは宣言した基準をイテレーションをまたいで再確認し、ワークフローの成果物を記録します。通常のプロンプトごとに実行されるゲートではありません。スキルが読み込まれただけで、すべてのワークフローや検証コマンドが始まることもありません。

## ディスパッチの結果を確認する

`oma doctor --profile` では、各ディスパッチロールに解決されたベンダーとモデルを表示します。現在のホストが処理しないロールを CLI から明示的に実行する場合は、`oma agent spawn <agent-id> <prompt> <session-id>` を使います。モデルの解決規則とプロバイダーごとの挙動は、[重要なデフォルト](./important-defaults.md) と[エージェント別モデル](../guide/per-agent-models.md)にまとめています。

フックでワークフローを起動できるのは、該当するホスト統合が有効な場合だけです。ネイティブスキルのルーティングはホストが行います。ワークフローのルーティングは選択したワークフローまたはフックに従います。通常のプロンプトだけで、特定のスキルやゲートが必ず実行されるわけではありません。

調整に関する任意の制御については、[セッションのクォータ上限](../guide/configuration-reference.md#session-quota-caps)、[`/orchestrate` の retry と探索ループ](../core-concepts/workflows.md#orchestrate)、[ワークスペースの割り当て](../core-concepts/parallel-execution.md#workspace-aware-pattern)を参照してください。

## 実務上のトレードオフ

OMA を使うと、ルーティング、実行手順、チェック、出力ファイルをチームで定義する場所ができます。その代わり、リポジトリの設定を最新に保ち、受入契約に含めるワークフローや検証コマンドを決める必要があります。貢献者間の一貫性が、最小限のインストールより重要な場合に、このトレードオフが役立ちます。

当初のポジショニングに関する議論は [issue #155](https://github.com/first-fluke/oh-my-agent/issues/155#issuecomment-4142133589)を参照してください。
