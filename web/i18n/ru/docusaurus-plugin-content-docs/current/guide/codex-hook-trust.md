# Руководство: доверие к Codex hooks

При установке oh-my-agent в проект он записывает конфигурацию hook в формате вендора, включая `.codex/hooks.json` для Codex CLI. Codex не запускает hook только потому, что он настроен. Его закрывают два подтверждения, и оба находятся в пользовательской конфигурации (`$CODEX_HOME/config.toml`, по умолчанию `~/.codex/config.toml`). Проект не может подтвердить собственные hooks:

1. **Доверие к проекту.** Каталог `.codex/` проекта (его `config.toml` и `hooks.json`) загружается только для доверенного проекта: `[projects."<path>"] trust_level = "trusted"`.
2. **Доверие к каждому hook.** Каждый неуправляемый hook, в области проекта или пользователя, требует запись `[hooks.state."<hooks.json path>:<event>:<group>:<handler>"]`, чей `trusted_hash` совпадает с текущим объявлением hook (command, timeout, matcher, async flag, status message).

Новый или изменённый hook показывает «Hooks need review» в TUI Codex. `codex exec` молча его пропускает.

---

## Что oh-my-agent записывает за вас

`oma install`, `oma update` и `oma link` записывают оба подтверждения для **собственных hooks oh-my-agent**. Это обработчики с именем `oma-hook-*` или запущенные через обёртку `oma-hook.sh`. Hash совпадает с тем, который Codex вычисляет, когда вы выбираете «Trust all and continue», поэтому hooks запускаются в первой сессии Codex без шага `/hooks`. Более поздний выпуск oh-my-agent, который меняет команду hook, записывает новый hash во время `oma update`, так что hooks остаются включёнными.

oh-my-agent правит только затронутые таблицы в `config.toml`. Он перечитывает результат и оставляет файл нетронутым, если изменилось бы что-то ещё. Он никогда:

- не подтверждает hook, который вы сами добавили в тот же `hooks.json`,
- не доверяет проекту, который вы пометили `trust_level = "untrusted"`,
- не включает снова hook, который вы выключили (`enabled = false`),
- не трогает Codex до того, как Codex создал свой домашний каталог.

Глобальная установка (`~/.codex/hooks.json`) получает только записи для каждого hook, потому что проекта, которому нужно доверять, нет.

## Когда hooks всё ещё проверяете вы

Если oh-my-agent не смог записать доверие, он печатает причину вместе с уведомлением:

```text
⚠ Codex hooks installed/updated but not trusted (<reason>) — run codex and use /hooks to trust them (untrusted hooks do not run).
```

Обычные случаи: `config.toml`, который не удаётся разобрать, проект, который вы пометили как недоверенный, или Codex ещё ни разу не запускался. В этом случае откройте проект в Codex, выполните `/hooks` и один раз включите hooks. Затем выполните `oma link codex`, чтобы последующие обновления сохраняли доверие.

---

## Процессы Codex, которые запускает oh-my-agent

Когда oh-my-agent сам запускает подпроцесс Codex (например, `oma agent spawn`), он также передаёт `--dangerously-bypass-hook-trust`. Этот флаг запускает включённые hooks без проверки hash. Он не снимает доверие к проекту. Флаг применяется только к процессам, которые запускает oh-my-agent, и никогда не записывается в вашу конфигурацию.

---

## Flag `[features] hooks` не требуется

Старые выпуски oh-my-agent записывали `[features] codex_hooks = true` в конфигурацию Codex. В Codex 0.124 этот флаг переименован в `hooks`, а hooks стали стабильной функцией, включённой по умолчанию, поэтому флаг не нужен. oh-my-agent не записывает ни один из этих ключей и удаляет устаревшие флаги `codex_hooks` и `child_agents_md` из таблицы `[features]`, если обнаруживает их.

## Итог

| Ситуация | Что вы делаете |
|:----------|:------------|
| Первая установка в проекте | Ничего: доверие записывает установщик |
| `oma update`, который меняет команду hook | Ничего: новый hash записывается |
| Установщик печатает «not trusted (…)» | Устраните причину или один раз выполните `/hooks` в Codex |
| Hook, который вы добавили в `.codex/hooks.json` | Проверьте его в `/hooks` самостоятельно |
