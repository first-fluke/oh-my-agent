# Руководство: мультиагентные проекты

## Когда использовать мультиагентную координацию

Ваша функция охватывает несколько доменов: API бэкенда, UI фронтенда, схему базы данных, мобильный клиент и QA-проверку. Один агент не может обработать весь объём, а домены должны продвигаться параллельно, не затрагивая файлы друг друга.

Мультиагентная координация подходит, когда:

- задача затрагивает два или более домена (frontend, backend, mobile, db, QA, debug, pm);
- между доменами есть API-контракты (например, REST-эндпоинт используется и веб-, и мобильным клиентом);
- вы хотите сократить календарное время за счёт параллельного выполнения;
- после реализации требуется QA-проверка всех доменов.

Если задача полностью относится к одному домену, используйте соответствующего агента напрямую.

## Полная последовательность: от /plan до /review

Рекомендуемый мультиагентный workflow следует строгому конвейеру из четырёх шагов.

### Шаг 1: /plan для требований и декомпозиции задачи

Workflow `/plan` выполняется inline, без запуска субагентов, и создаёт структурированный план.

```
/plan
```

Что происходит:

1. **Сбор требований:** PM-агент спрашивает о целевых пользователях, основных функциях, ограничениях и целях развёртывания.
2. **Анализ технической реализуемости:** использует настроенный провайдер code intelligence, чтобы найти в кодовой базе повторно используемый код и архитектурные паттерны. Нативный поиск предназначен только для путей вне проекта или игнорируемых путей.
3. **Определение API-контрактов:** проектирует контракты эндпоинтов (метод, путь, схемы запроса и ответа, аутентификация, ответы с ошибками), сохраняет их в `.agents/results/api-contracts/` (артефакты запуска), а после коммита перемещает долговечные спецификации в `docs/plans/contracts/`.
4. **Декомпозиция:** разбивает проект на выполнимые задачи. Для каждой указывает агента, название, критерии приёмки, приоритет (P0–P3) и зависимости.
5. **Ревью плана пользователем:** показывает полный план для подтверждения. Workflow не продолжится без явного подтверждения пользователя.
6. **Сохранение плана:** записывает утверждённый план в `.agents/results/plan-{sessionId}.json` и сохраняет сводку в памяти.

Файл `.agents/results/plan-{sessionId}.json` служит входом и для `/work`, и для `/orchestrate`.

### Шаг 2: /work или /orchestrate для выполнения

Доступны два пути выполнения:

| Аспект | /work | /orchestrate |
|:-------|:-----------|:-------------|
| **Взаимодействие** | Интерактивное (пользователь подтверждает каждый этап) | Автоматическое (выполнение до завершения) |
| **Планирование PM** | Встроено (шаг 2 запускает PM-агента) | Загружает существующий план; если его нет, создаёт его inline |
| **Чекпоинт пользователя** | После ревью плана (шаг 3) | Inline-план всё равно проходит шлюз ревью до fan-out |
| **Постоянный режим** | Да (его нельзя завершить до окончания) | Да (его нельзя завершить до окончания) |
| **Лучше всего подходит** | Для первого использования и сложных проектов, требующих контроля | Для повторных запусков и чётко определённых задач |

#### /work: интерактивный мультиагентный конвейер

```
/work
```

1. Анализирует запрос пользователя и определяет задействованные домены.
2. Запускает PM-агента для декомпозиции задачи (создаёт `plan-{sessionId}.json`).
3. Показывает план для подтверждения пользователя. **Останавливается до подтверждения.**
4. Запускает агентов по уровням приоритета (сначала P0); задачи одного уровня выполняются параллельно.
5. Отслеживает прогресс агентов по файлам памяти.
6. Запускает QA-агента для проверки всех результатов (OWASP Top 10, производительность, доступность, качество кода).
7. Если QA обнаруживает проблемы CRITICAL или HIGH, заново запускает ответственного агента с выводами QA. Повторяет это до двух раз для каждой проблемы. Если та же проблема сохраняется, активирует **цикл исследования**: генерирует 2–3 альтернативных подхода, запускает агентов того же типа с разными гипотезами в отдельных рабочих пространствах, оценивает результаты QA и принимает лучший.

#### /orchestrate: автоматическое параллельное выполнение

```
/orchestrate
```

1. Загружает `.agents/results/plan-{sessionId}.json`; если пригодного файла плана нет, создаёт план inline через `/plan`.
2. Инициализирует сессию с ID формата `session-YYYYMMDD-HHMMSS`.
3. Создаёт `orchestrator-session.md` и `task-board.md` в каталоге памяти.
4. Запускает агентов по уровням приоритета; каждый получает описание задачи, API-контракты и контекст.
5. Отслеживает прогресс, периодически читая файлы `progress-{agent}.md`.
6. Проверяет каждого завершившегося агента через `verify.sh`. PASS (код выхода 0) принимает результат; FAIL (код выхода 1) запускает агента повторно с контекстом ошибки (не более двух повторов); постоянная ошибка запускает цикл исследования.
7. Собирает все файлы `result-{agent}.md` и формирует итоговый отчёт.

### Шаг 3: agent spawn для управления агентами на уровне CLI

Команда `agent spawn` — низкоуровневый механизм, который workflow вызывает внутри. Её можно использовать и напрямую:

```bash
oma agent spawn backend "Implement user auth API with JWT" session-20260324-143000 -w ./api
```

**Все флаги:**

| Флаг | Описание |
|:-----|:-----------|
| `--vendor <vendor>` | Переопределение CLI-вендора (antigravity/claude/codex/cursor/opencode/qwen/grok/pi). Переопределяет разрешение модели для этого запуска. |
| `-w, --workspace <path>` | Рабочий каталог агента. Если не указан, определяется автоматически по конфигурации монорепозитория. |
| `--task-id <id>` | Привязывает запуск к задаче в плане сессии; по умолчанию используется ID агента. |
| `--isolation worktree` | Создаёт git worktree для запуска; по умолчанию дополнительной изоляции нет. |
| `--read-only` | Ограничивает дочерний процесс инструментами инспекции и отключает флаги auto-approve. |

**Порядок выбора вендора** (от первого совпадения к последнему):

1. Флаг `--vendor` в командной строке
2. Переопределение в `agents:` файла `oma-config.yaml`
3. Значения по умолчанию активного `model_preset`

Подробности настройки см. в [моделях агентов](./per-agent-models.md).

**Автоматическое определение workspace** проверяет конфигурации монорепозитория в таком порядке: `pnpm-workspace.yaml`, workspaces в `package.json`, `lerna.json`, `nx.json`, `turbo.json`, `mise.toml`. Каждый каталог workspace получает баллы по ключевым словам типа агента (например, «web», «frontend», «client» для фронтенд-агента). Если конфигурации монорепозитория нет, используются фиксированные кандидаты вроде `apps/web`, `apps/frontend`, `frontend/` и других.

**Разрешение prompt:** аргумент `<prompt>` может быть встроенным текстом или путём к файлу. Если путь указывает на существующий файл, CLI читает его содержимое и использует его как prompt. CLI также добавляет специфичные для вендора execution protocols из `.agents/skills/_shared/runtime/execution-protocols/{vendor}.md`.

### Шаг 4: /review для QA-проверки

```
/review
```

Workflow ревью запускает полный QA-конвейер:

1. **Определение области:** спрашивает, что проверить (конкретные файлы, ветку функции или весь проект).
2. **Автоматические проверки безопасности:** запускает `npm audit`, `bandit` или эквивалент.
3. **Ручная проверка OWASP Top 10:** инъекции, сломанная аутентификация, утечки чувствительных данных, контроль доступа, неверная конфигурация, небезопасная десериализация, уязвимые компоненты, недостаточное логирование.
4. **Анализ производительности:** N+1-запросы, отсутствующие индексы, неограниченная пагинация, утечки памяти, лишние перерисовки, размеры bundle.
5. **Доступность:** WCAG 2.1 AA, включая семантический HTML, ARIA, клавиатурную навигацию, контраст цветов и управление фокусом.
6. **Качество кода:** имена, обработка ошибок, покрытие тестами, строгий режим TypeScript, неиспользуемые импорты, паттерны async/await.
7. **Отчёт:** результаты делятся на CRITICAL / HIGH / MEDIUM / LOW и содержат `file:line`, описание и код исправления.

Для больших областей workflow делегирует работу субагенту QA. С опцией `--fix` запускается **цикл Fix-Verify**: доменные агенты исправляют проблемы CRITICAL/HIGH, затем ревью повторяется до трёх раз.

## Стратегия ID сессии

Каждая сессия оркестрации получает уникальный идентификатор формата:

```
session-YYYYMMDD-HHMMSS
```

Пример: `session-20260324-143052`

ID сессии используется для:

- имён файлов памяти (`orchestrator-session.md`, `task-board.md`);
- отслеживания процессов агентов через PID-файлы в системном временном каталоге (`/tmp/subagent-{session-id}-{agent-id}.pid`);
- связывания log-файлов (`/tmp/subagent-{session-id}-{agent-id}.log`);
- группировки результатов в `.agents/results/parallel-{timestamp}/`.

ID сессии создаётся на шаге 2 `/orchestrate` и передаётся всем запущенным агентам. Благодаря этому все агенты, логи и результаты одной сессии можно отследить вместе.

## Назначение workspace по доменам

Каждый агент запускается в изолированном рабочем пространстве, чтобы избежать конфликтов файлов. Назначение следует этим правилам:

### Автоматическое определение

Если `-w` не указан (или задан как `.`), CLI:

1. проверяет конфигурации монорепозитория (`pnpm-workspace.yaml`, `package.json`, `lerna.json`, `nx.json`, `turbo.json`, `mise.toml`);
2. раскрывает glob-шаблоны (например, `apps/*`) в существующие каталоги;
3. оценивает каждый каталог по ключевым словам типа агента:

| Тип агента | Ключевые слова (в порядке приоритета) |
|:-----------|:--------------------------------------|
| frontend | web, frontend, client, ui, app, dashboard, admin, portal |
| backend | api, backend, server, service, gateway, core |
| mobile | mobile, ios, android, native, rn, expo |

4. точное совпадение имени каталога получает 100 баллов, совпадение по содержимому — 50, наличие слова в пути — 25;
5. выбирается каталог с наибольшим результатом.

### Резервные кандидаты

Если конфигурации монорепозитория нет, CLI проверяет пути в следующем порядке:

- **frontend:** `apps/web`, `apps/frontend`, `apps/client`, `packages/web`, `packages/frontend`, `frontend`, `web`, `client`
- **backend:** `apps/api`, `apps/backend`, `apps/server`, `packages/api`, `packages/backend`, `backend`, `api`, `server`
- **mobile:** `apps/mobile`, `apps/app`, `packages/mobile`, `mobile`, `app`

Если ничего не найдено, агент запускается в текущем каталоге (`.`).

### Явное переопределение

Доступно всегда:

```bash
oma agent spawn frontend "Build landing page" session-id -w ./packages/web-app
```

## Правило контрактов в первую очередь

API-контракты — механизм синхронизации между агентами. Правило означает следующее:

1. **Контракты определяются до начала реализации.** Шаг 3 workflow `/plan` создаёт API-контракты и сохраняет их в `.agents/results/api-contracts/` (либо в `docs/plans/contracts/` для долговечных спецификаций).

2. **Каждый агент получает относящиеся к нему контракты в контексте.** На шаге 3 `/orchestrate` агент получает «описание задачи, API-контракты и релевантный контекст».

3. **Контракты задают границу интерфейса.** Контракт описывает:
   - HTTP-метод и путь;
   - схему тела запроса (с типами);
   - схему тела ответа (с типами);
   - требования к аутентификации;
   - форматы ответов с ошибками.

4. **Нарушения контракта выявляются во время мониторинга.** На шаге 5 `/work` настроенный провайдер code intelligence проверяет соответствие API между агентами бэкенда, фронтенда и мобильного приложения. Нативный поиск предназначен только для путей вне проекта или игнорируемых путей.

5. **QA проверяет соблюдение контрактов.** Alignment Review QA-агента (шаг 6 в ultrawork, шаг 6 в work) напрямую сравнивает реализацию с планом, включая API-контракты.

Без контрактов агент бэкенда может вернуть `{ "user_id": 1 }`, а фронтенд будет ожидать `{ "userId": 1 }`. Правило контрактов в первую очередь предотвращает такие ошибки интеграции.

## Шлюзы слияния: 4 условия

До того как считать мультиагентную работу завершённой, должны выполняться четыре условия:

### 1. Объявленные проверки проходят

У каждого критерия приёмки есть соответствующая проверка, а объявленные планом проверки завершились успешно. Сборка включается только тогда, когда её требует проектный шлюз задачи; result contract фиксирует фактические аргументы и код выхода.

### 2. Тесты проходят

Все существующие тесты продолжают проходить, а новые тесты покрывают реализованную функцию. QA-агент проверяет покрытие в рамках Code Quality Review.

### 3. Изменены только запланированные файлы

Агенты не должны менять файлы вне своей области. Шаг проверки убеждается, что изменены только файлы, относящиеся к задаче. Это предотвращает непреднамеренные побочные эффекты в общем коде.

### 4. QA-ревью завершено без блокеров

После ревью QA не должно оставаться результатов CRITICAL или HIGH. Результаты MEDIUM и LOW можно задокументировать для будущих спринтов, но блокеры нужно устранить.

В workflow ultrawork эти условия выражаются явными фазовыми шлюзами (PLAN_GATE, IMPL_GATE, VERIFY_GATE, REFINE_GATE, SHIP_GATE), каждый из которых должен пройти все пункты чек-листа.

## Примеры запуска

### Запуск одного агента

```bash
# Spawn backend agent with Gemini (default)
oma agent spawn backend "Implement /api/users CRUD endpoint per API contract" session-20260324-143000

# Spawn frontend agent with Claude, explicit workspace
oma agent spawn frontend "Build user dashboard with React" session-20260324-143000 --vendor claude -w ./apps/web

# Spawn from a prompt file
oma agent spawn backend ./prompts/auth-api.md session-20260324-143000 -w ./api
```

### Параллельное выполнение через agent parallel

С YAML-файлом задач:

```yaml
# tasks.yaml
tasks:
  - agent: backend
    task: "Implement user authentication API with JWT tokens"
    workspace: ./api
  - agent: frontend
    task: "Build login page and auth flow UI"
    workspace: ./web
  - agent: mobile
    task: "Implement mobile auth screens with biometric support"
    workspace: ./mobile
```

```bash
oma agent parallel tasks.yaml
```

В inline-режиме:

```bash
oma agent parallel --inline \
  "backend:Implement user auth API:./api" \
  "frontend:Build login page:./web" \
  "mobile:Implement auth screens:./mobile"
```

Фоновый режим (без ожидания):

```bash
oma agent parallel tasks.yaml --no-wait
# Returns immediately, results written to .agents/results/parallel-{timestamp}/
```

С переопределением вендора:

```bash
oma agent parallel tasks.yaml --vendor claude
```

## Анти-паттерны

### 1. Формальное одобрение плана

`/orchestrate` может создать план через `/plan` inline, если пригодного файла плана нет. Inline-план всё равно проходит шлюз ревью `/plan`, а последующий fan-out следует утверждённой декомпозиции. Для больших мультидоменной задач запускайте `/plan` заранее, чтобы получить долговечный трекер в `docs/plans/work/` и возможность уточнить декомпозицию до запуска агентов.

### 2. Пересекающиеся workspace

Назначение двух агентов в один рабочий каталог. Это приводит к конфликтам файлов, когда изменения одного агента перезаписывают изменения другого. Всегда используйте отдельные рабочие пространства.

### 3. Отсутствующие API-контракты

Запуск агентов бэкенда и фронтенда без предварительного определения контрактов. Они начнут делать несовместимые предположения о форматах данных, именах полей и ошибках.

### 4. Игнорирование результатов QA

Отношение к QA-ревью как к необязательному шагу. Результаты CRITICAL и HIGH означают реальные ошибки, которые проявятся в production. Workflow обеспечивает цикл до устранения блокеров.

### 5. Ручная координация файлов

Попытка вручную сливать результаты агентов вместо передачи интеграции шагам проверки и QA-конвейеру. Автоматизированный конвейер обнаруживает проблемы, которые легко пропустить при ручной проверке.

### 6. Чрезмерный параллелизм

Запуск задач P1 до завершения задач P0. Уровни приоритета нужны потому, что задачи P1 часто зависят от результатов P0. Workflow автоматически соблюдают порядок уровней.

### 7. Пропуск верификации

Использование `agent spawn` напрямую без записи result contract. После запуска задачи выполните закреплённые проверки и завершите структурированный claim; см. [результаты агентов и возобновление](/docs/guide/agent-results-and-resume). Затем проверка workflow выявит ошибки и выход за область до повторного использования результата.

## Проверка кросс-доменной интеграции

После завершения всех задач отдельных агентов нужно проверить интеграцию между доменами:

1. **Соответствие API-контрактам:** настроенный провайдер code intelligence проверяет, что реализации бэкенда соответствуют контрактам, которые использует фронтенд и мобильное приложение. Нативный поиск предназначен только для путей вне проекта или игнорируемых путей.

2. **Согласованность типов:** типы TypeScript, dataclass в Python и модели Dart, общие для доменов, должны использовать одинаковые имена и типы полей.

3. **Поток аутентификации:** если бэкенд реализует JWT-аутентификацию, фронтенд должен правильно передавать токены в заголовках, а мобильное приложение — хранить и обновлять их.

4. **Обработка ошибок:** все потребители API должны обрабатывать задокументированные ответы с ошибками. Если бэкенд возвращает `{ "error": "unauthorized", "code": 401 }`, все клиенты должны обрабатывать этот формат.

5. **Соответствие схеме базы данных:** если агент базы данных создаёт миграции, модели ORM бэкенда должны точно соответствовать схеме.

Alignment Review QA-агента (шаг 6 в ultrawork, шаг 6 в work) систематически выполняет эту кросс-доменную проверку.

## Когда всё готово

Мультиагентный проект завершён, когда:

- все агенты всех уровней приоритета завершили работу успешно;
- скрипты проверки проходят для каждого агента (код выхода 0);
- QA-ревью сообщает о нулевом числе результатов CRITICAL и HIGH;
- подтверждено соответствие API-контрактов между доменами;
- сборка успешна и все тесты проходят;
- итоговый отчёт записан в память и представлен пользователю;
- пользователь дал финальное подтверждение (в `/work` и SHIP_GATE ultrawork).
