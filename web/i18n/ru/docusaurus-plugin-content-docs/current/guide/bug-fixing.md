# Руководство: исправление ошибок

## Когда использовать workflow отладки

Используйте `/debug` (или скажите «fix bug», «fix error», «debug» на естественном языке), когда нужно диагностировать и исправить конкретную ошибку. Workflow даёт структурированный воспроизводимый подход к отладке и помогает избежать типичной ловушки: исправления симптома вместо корневой причины.

Workflow отладки поддерживает всех настроенных вендоров. Шаги 1–5 выполняются inline. Шаг 6 (сканирование похожих паттернов) может делегировать работу субагенту `debug-investigator`, если область поиска широкая (10+ файлов или ошибка затрагивает несколько доменов); после него выполняется запись в памяти на шаге 7.

---

## Шаблон отчёта об ошибке

Сообщите при обнаружении ошибки как можно больше сведений из списка ниже. Каждое поле помогает workflow отладки быстрее сузить область поиска.

### Обязательные поля

| Поле | Описание | Пример |
|:------|:-----------|:--------|
| **Сообщение об ошибке** | Точный текст ошибки или stack trace | `TypeError: Cannot read properties of undefined (reading 'id')` |
| **Шаги воспроизведения** | Упорядоченные действия, вызывающие ошибку | 1. Войти как admin. 2. Перейти на /users. 3. Нажать «Delete» у любого пользователя. |
| **Ожидаемое поведение** | Что должно произойти | Пользователь удалён и убран из списка. |
| **Фактическое поведение** | Что происходит на самом деле | Страница падает с белым экраном. |

### Необязательные поля (настоятельно рекомендуются)

<!-- oma-docs:ignore-start -->
| Поле | Описание | Пример |
|:------|:-----------|:--------|
| **Окружение** | Браузер, ОС, версия Node, устройство | Chrome 124, macOS 15.3, Node 22.1 |
| **Частота** | Всегда, иногда, только при первом запуске | Воспроизводится всегда |
| **Недавние изменения** | Что изменилось перед появлением ошибки | Слит PR #142 (функция удаления пользователей) |
| **Связанный код** | Файлы или функции, которые вы подозреваете | `src/api/users.ts`, `deleteUser()` |
| **Логи** | Серверные логи, вывод консоли | `[ERROR] UserService.delete: user.organizationId is undefined` |
| **Скриншоты/записи** | Визуальные свидетельства | Скриншот экрана ошибки |
<!-- oma-docs:ignore-end -->

Чем больше контекста вы дадите заранее, тем меньше дополнительных вопросов потребуется workflow отладки.

## Триаж по серьёзности (P0–P3)

Серьёзность определяет порядок обработки ошибки и скорость её исправления.

### P0: критическая (немедленная реакция)

**Определение:** production недоступен, данные теряются или повреждаются, активна брешь в безопасности.

**Ожидаемая реакция:** отложите всё остальное. Эта задача остаётся единственной до устранения проблемы.

**Примеры:**
- Обходится система аутентификации; все пользователи получают доступ к admin-эндпоинтам.
- Миграция базы данных повредила таблицу пользователей; аккаунты недоступны.
- Обработка платежей дважды списывает деньги с клиентов.
- API-эндпоинт возвращает персональные данные других пользователей.

**Подход к отладке:** пропустите полный шаблон. Передайте сообщение об ошибке и любой stack trace. Workflow сразу начинает с шага 2 (воспроизведение).

### P1: высокая (в этой сессии)

**Определение:** основная функция сломана для значительного числа пользователей. Обходной путь может существовать, но его нельзя считать долгосрочным решением.

**Ожидаемая реакция:** исправьте ошибку в текущей рабочей сессии. Не начинайте новые функции, пока проблема не решена.

**Примеры:**
- Поиск не возвращает результаты для запросов со специальными символами.
- Загрузка файла завершается ошибкой для файлов больше 5 MB (лимит должен быть 50 MB).
- Мобильное приложение падает при запуске на устройствах с Android 14.
- Письма для сброса пароля не отправляются (сломана интеграция почтового сервиса).

**Подход к отладке:** полный семиэтапный цикл. После исправления рекомендуется QA-ревью.

### P2: средняя (в текущем спринте)

**Определение:** функция работает, но с ухудшенным поведением. Это влияет на удобство использования, но не на саму функциональность.

**Ожидаемая реакция:** запланируйте исправление в текущем спринте. Исправьте до следующего релиза.

**Примеры:**
- Сортировка таблицы чувствительна к регистру («apple» сортируется после «Zebra»).
- В тёмном режиме текст в панели настроек нечитаем.
- Время ответа API для эндпоинта /users составляет 8 секунд (должно быть меньше 1 секунды).
- При пустом списке пагинация показывает «Page 1 of 0».

**Подход к отладке:** полный семиэтапный цикл. Включите ошибку в регрессионный набор QA.

### P3: низкая (бэклог)

**Определение:** косметическая проблема, крайний случай или небольшое неудобство.

**Ожидаемая реакция:** добавьте в бэклог. Исправьте при возможности или объедините с похожими изменениями.

**Примеры:**
- В тексте подсказки опечатка: «Delet» вместо «Delete».
- Предупреждение консоли об устаревшем React lifecycle method.
- Выравнивание footer смещено на 2 пикселя при ширине viewport от 768 до 800px.
- Индикатор загрузки остаётся ещё 200 мс после появления содержимого.

**Подход к отладке:** полный цикл может не понадобиться. Достаточно прямого исправления с регрессионным тестом.

## Семь этапов цикла отладки подробно

Workflow `/debug` выполняет эти этапы по порядку. Он использует настроенный провайдер code intelligence. Нативный поиск предназначен только для путей вне проекта или игнорируемых путей, когда этот провайдер недоступен или отвечает слишком долго.

### Шаг 1: сбор информации об ошибке

Workflow запрашивает у пользователя (или получает из запроса):
- сообщение об ошибке и stack trace;
- шаги воспроизведения;
- ожидаемое и фактическое поведение;
- сведения об окружении.

Если сообщение об ошибке уже есть в промпте, workflow сразу переходит к шагу 2.

### Шаг 2: воспроизведение ошибки

**Используемые инструменты:** настроенные инструменты поиска и символов или локальные `rg` и scoped reads, если настроенные инструменты недоступны.

Цель — найти ошибку в кодовой базе: точную строку, где выбрасывается исключение, функцию, формирующую неверный результат, или условие, вызывающее неожиданное поведение.

Этот шаг превращает сообщённый пользователем симптом («страница падает») в точку в кодовой базе (`src/api/users.ts:47, deleteUser() throws TypeError`).

### Шаг 3: диагностика корневой причины

**Используемые инструменты:** навигация по ссылкам и символам, если доступна, затем целевое локальное чтение, если нет.

Workflow идёт от места ошибки назад по цепочке и ищет настоящую причину. Он проверяет следующие распространённые паттерны корневых причин:

| Паттерн | На что смотреть |
|:--------|:----------------|
| **Доступ к null/undefined** | Отсутствуют null-проверки, нужен optional chaining, переменные не инициализированы |
| **Состояния гонки** | Асинхронные операции завершаются не по порядку, отсутствует await, изменяемое состояние разделяется |
| **Отсутствие обработки ошибок** | Нет try/catch, отклонённый promise не обработан, отсутствует error boundary |
| **Неверные типы данных** | Ожидалось число, пришла строка; отсутствует приведение типов; неверная схема |
| **Устаревшее состояние** | Состояние React не обновляется, кэшированные значения не инвалидируются, замыкание захватывает старое значение |
| **Отсутствие валидации** | Ввод пользователя не санитизируется, тело API-запроса не проверяется, граничные условия не проверяются |

Диагностируйте корневую причину, а не симптом. Если `user.id` равен undefined, выясните, почему `user` оказался undefined в этой точке пути выполнения, а не просто добавляйте защиту от undefined.

### Шаг 4: предложение минимального исправления

Workflow показывает:
1. найденную корневую причину (с доказательствами из трассировки кода);
2. предлагаемое исправление (изменяется только необходимое);
3. объяснение, почему исправление устраняет корневую причину, а не только симптом.

Workflow показывает предложение до редактирования. Если изменение не было заранее разрешено запросом или execution policy, он ждёт подтверждения; имеющееся разрешение позволяет продолжить без повторного вопроса.

**Принцип минимального исправления:** изменяйте как можно меньше строк. Не выполняйте рефакторинг, не улучшайте стиль кода и не добавляйте несвязанные функции. Исправление должно быть понятным при ревью менее чем за 2 минуты.

### Шаг 5: применение исправления и написание регрессионного теста

На этом шаге выполняются два действия:

1. **Реализация исправления:** применяется утверждённое минимальное изменение.
2. **Написание регрессионного теста:** тест должен:
   - воспроизводить исходную ошибку (без исправления тест должен завершаться неуспешно);
   - проверять работу исправления (с исправлением тест должен проходить);
   - предотвращать повторное появление той же ошибки в будущих изменениях.

Регрессионный тест — самый важный результат workflow отладки. Без него любое будущее изменение может вернуть ту же ошибку.

### Шаг 6: сканирование похожих паттернов

После применения исправления workflow ищет во всей кодовой базе тот же паттерн, который вызвал ошибку.

**Используемые инструменты:** настроенный поиск паттернов или локальный scoped search с паттерном, определённым как корневая причина.

Например, если ошибка возникла из-за обращения к `user.organization.id` без проверки того, что `organization` не равна null, поиск находит все остальные обращения к `organization.id` без проверки на null.

**Критерии делегирования субагенту:** workflow запускает субагента `debug-investigator`, если:
- ошибка затрагивает несколько доменов (например, одновременно фронтенд и бэкенд);
- сканирование похожего паттерна охватывает 10+ файлов;
- для полной диагностики нужна глубокая трассировка зависимостей.

Способы запуска для разных вендоров:

| Вендор | Способ запуска |
|:-------|:---------------|
| Claude Code | Agent tool с `.claude/agents/debug-investigator.md` |
| Codex CLI | Запрос субагента через модель, результаты в JSON |
| Gemini CLI | `oma agent spawn debug "scan prompt" {session_id} -w {workspace}` |
| Antigravity / Fallback | `oma agent spawn debug "scan prompt" {session_id} -w {workspace}` |

Все найденные уязвимые места сообщаются. Подтверждённые экземпляры исправляются в рамках той же сессии.

### Шаг 7: документирование ошибки

Workflow записывает файл памяти с такими сведениями:
- симптом и корневая причина;
- применённое исправление и изменённые файлы;
- расположение регрессионного теста;
- найденные в кодовой базе похожие паттерны.

## Шаблон промпта для /debug

При запуске workflow отладки можно передать структурированный промпт:

```
/debug

Error: TypeError: Cannot read properties of undefined (reading 'id')
Stack trace:
  at deleteUser (src/api/users.ts:47:23)
  at handleDelete (src/routes/users.ts:112:5)

Steps to reproduce:
1. Log in as admin
2. Navigate to /users
3. Click "Delete" on a user whose organization was deleted

Expected: User is deleted
Actual: 500 Internal Server Error

Environment: Node 22.1, PostgreSQL 16
```

**Почему такая структура работает:**

- **Ошибка + stack trace** позволяют шагу 2 сразу найти код (`search_for_pattern` с «deleteUser» находит функцию, а `find_symbol` указывает точное место).
- **Шаги воспроизведения** с конкретным условием запуска («пользователь, чья organization была удалена») подсказывают корневую причину (null foreign key).
- **Окружение** исключает ложные версии, связанные с различиями версий.

Для более простых ошибок подойдёт короткий промпт:

```
/debug The login page shows "Invalid credentials" even with correct password
```

Workflow при необходимости запросит дополнительные сведения.

## Сигналы эскалации

Эти сигналы означают, что ошибка требует выхода за пределы стандартного цикла отладки:

### Сигнал 1: одно исправление уже пробовали дважды

Если workflow предложил и применил исправление, но та же ошибка повторилась, проблема глубже первоначальной диагностики. Пересмотрите причину. Если альтернативы стоит проверить и существующий бюджет восстановления это позволяет, используйте **цикл исследования** в активном workflow (ultrawork, orchestrate, work):

- сформировать 2–3 альтернативные гипотезы корневой причины;
- изолировать каждый эксперимент и сохранить его baseline, доказательства и несвязанную работу;
- выбрать подход, который соответствует требуемому поведению и сопоставимым критериям измерения, затем проверить интегрированный результат.

### Сигнал 2: корневая причина в нескольких доменах

Ошибка фронтенда вызвана изменением бэкенда, которое, в свою очередь, вызвано миграцией схемы базы данных. Если корневая причина пересекает границы доменов, переключитесь на `/work` или `/orchestrate`, чтобы подключить нужных доменных агентов.

**Пример:** фронтенд показывает «undefined» вместо имени пользователя. Бэкенд возвращает null в `user.display_name`. Миграция базы добавила столбец, но в существующих строках остались значения NULL. Исправление требует миграции базы (backfill), обработки null на бэкенде и fallback-отображения на фронтенде.

### Сигнал 3: нет среды воспроизведения

Ошибка проявляется только в production и не воспроизводится локально. Возможные признаки:
- конфигурация отличается между окружениями;
- состояние гонки проявляется только под production-нагрузкой;
- поведение стороннего сервиса отличается между staging и production.

**Действие:** соберите production-логи, запросите доступ к production-мониторингу и рассмотрите добавление instrumentation/logging до попытки исправления.

### Сигнал 4: сбой тестовой инфраструктуры

Регрессионный тест нельзя написать, потому что инфраструктура тестов сломана, отсутствует или недостаточна.

**Действие:** сначала исправьте тестовую инфраструктуру (или используйте `oma install` для её настройки), затем вернитесь к workflow отладки. Если executable check неприменим, укажите причину в result contract, а не придумывайте успешную проверку.

## Чек-лист проверки после исправления

После применения исправления и регрессионного теста проверьте:

- [ ] **Регрессионный тест не проходит без исправления:** временно отмените исправление и убедитесь, что тест обнаруживает ошибку.
- [ ] **Регрессионный тест проходит с исправлением:** примените исправление и убедитесь, что тест успешен.
- [ ] **Соответствующие существующие проверки проходят:** запустите проверки проекта, покрывающие изменённое поведение. Выполняйте build только когда задача явно этого требует.
- [ ] **Похожие паттерны просканированы:** шаг 6 завершён, все найденные экземпляры исправлены или задокументированы.
- [ ] **Исправление минимально:** изменены только необходимые строки, несвязанный рефакторинг отсутствует.
- [ ] **Корневая причина задокументирована:** файл памяти содержит симптом, корневую причину, исправление, изменённые файлы, расположение регрессионного теста и найденные похожие паттерны.

## Критерии завершения

Workflow отладки завершён, когда:

1. Корневая причина выявлена и задокументирована, а не только описан симптом.
2. Минимальное исправление применено в рамках разрешений задачи.
3. Есть регрессионный тест, который не проходит без исправления и проходит с ним.
4. Кодовая база просканирована на похожие паттерны, а все подтверждённые экземпляры обработаны.
5. Отчёт об ошибке записан в памяти и содержит симптом, корневую причину, применённое исправление, изменённые файлы, расположение регрессионного теста и найденные похожие паттерны.
6. Все существующие тесты продолжают проходить после исправления.
