# Руководство: мониторинг через дашборд

## Две команды дашборда

oh-my-agent предоставляет два дашборда реального времени для мониторинга активности агентов во время мультиагентных workflow.

| Команда | Интерфейс | URL | Технология |
|:--------|:---------|:----|:-----------|
| `oma dashboard terminal` | Терминал (TUI) | N/A (рендерится в терминале) | наблюдатель файлов chokidar, рендеринг picocolors |
| `oma dashboard web` | Браузер | `http://127.0.0.1:9847` (токен выводится при запуске) | HTTP-сервер, WebSocket, наблюдатель файлов chokidar |

По умолчанию оба дашборда следят за `.agents/state/memories/`. Если файлы координации хранятся в другом месте, задайте `MEMORIES_DIR`. Дашборд автоматически не переключается на `.serena/memories/`.

### Терминальный дашборд

```bash
oma dashboard terminal
```

Команда выводит непосредственно в терминал интерфейс с рамками. Он автоматически обновляется при изменении файлов памяти. Нажмите `Ctrl+C`, чтобы выйти.


**Символы статуса:**
- `●` (зелёный): выполняется
- `✓` (голубой): завершено

- `○` (жёлтый): заблокировано
- `◌` (приглушённый): ожидает запуска

### Веб-дашборд

```bash
oma dashboard web
```

Запускает веб-сервер только для loopback на порту 9847 (можно изменить через `DASHBOARD_PORT`). OMA выводит URL с `127.0.0.1`; откройте точный URL и сохраните токен. Страница использует токен для `/api/state`, `/api/recap` и обновлений WebSocket. Запросы без токена получают ответ `401`.

```bash
# Custom port
DASHBOARD_PORT=8080 oma dashboard web

# Custom memories directory
MEMORIES_DIR=/path/to/.agents/state/memories oma dashboard web

# The process also serves the recap view at /recap; use the tokenized URL it prints.
```

Веб-дашборд показывает те же сведения, что и терминальный, но в оформленном UI с тёмной темой:
- индикатор состояния подключения (Connected / Disconnected / Connecting с автоматическим переподключением);
- ID сессии и строка состояния;
- таблица статусов агентов с анимированными точками состояния;
- лента последних действий;
- автоматически обновляемые временные метки.

## Рекомендуемая раскладка из 3 терминалов

Для мультиагентных workflow рекомендуется использовать три панели терминала:

```
┌────────────────────────────────┬────────────────────────────────┐
│                                │                                │
│   Terminal 1: Main Agent       │   Terminal 2: Dashboard        │
│                                │                                │
│   $ gemini                     │   $ oma dashboard terminal              │
│   > /orchestrate               │                                │
│   ...                          │   ╔═══════════════════════╗    │
│                                │   ║ Serena Dashboard      ║    │
│                                │   ║ Session: ...          ║    │
│                                │   ╚═══════════════════════╝    │
│                                │                                │
├────────────────────────────────┴────────────────────────────────┤
│                                                                 │
│   Terminal 3: Ad-hoc commands                                   │
│                                                                 │
│   $ oma agent status session-20260324-143052 backend frontend   │
│   $ oma stats get                                                   │
│   $ oma verify agent backend -w ./api                           │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

**Терминал 1** запускает основную сессию агента (Gemini CLI, Claude Code, Codex и т. д.), где вы взаимодействуете с workflow вроде `/orchestrate` или `/work`.

**Терминал 2** запускает дашборд для пассивного мониторинга. Он обновляется автоматически и не требует действий.

**Терминал 3** предназначен для разовых команд: проверки статуса агентов, запуска верификаций, просмотра статистики или отладки проблем.

## Источники данных в .agents/state/memories/

Дашборды читают каталог `.agents/state/memories/`. Агенты и workflow заполняют его координационными файлами во время выполнения. Для проекта, где состояние хранится в другом месте, используйте `MEMORIES_DIR`.

### Типы файлов и их содержимое

| Шаблон файла | Кто создаёт | Содержимое |
|:-------------|:----------|:----------|
| `orchestrator-session.md` | шаг 2 `/orchestrate` | ID сессии, время запуска, статус (RUNNING/COMPLETED/FAILED), версия workflow |
| `session-{workflow}.md` | `/work`, `/ultrawork` | Метаданные сессии, прогресс фаз, сводка запроса пользователя |
| `task-board.md` | Workflow оркестрации | Таблица с назначениями агентов, статусами и задачами |
| `progress-{agent}.md` | Каждый запущенный агент | Номер хода, текущая работа, промежуточные результаты |
| `result-{agent}.md` | Каждый завершивший агент | Итоговый статус (COMPLETED/FAILED), изменённые файлы, найденные проблемы, результаты |
| `debug-{id}.md` | workflow `/debug` | Диагноз ошибки, корневая причина, применённое исправление, расположение регрессионного теста |
| `experiment-ledger-{sessionId}.md` | Фактические эксперименты | Сопоставимые доказательства baseline/candidate, обязательные проверки и решения |
| `lessons-{sessionId}.md` | Когда повторно используемая причина подтверждена доказательствами | Уроки в рамках сессии; генерация по оценке не выполняется |

### Как дашборд читает эти файлы

Дашборд использует несколько стратегий для извлечения информации:

1. **Обнаружение сессии:** сначала ищет `orchestrator-session.md`, затем переключается на самый недавно изменённый файл `session-*.md`. Статус извлекается по ключевым словам: `RUNNING`, `IN PROGRESS`, `COMPLETED`, `DONE`, `FAILED`, `ERROR`.

2. **Разбор task board:** читает `task-board.md` как таблицу Markdown. Извлекает имя агента, статус и описание задачи из столбцов.

3. **Обнаружение агентов:** если task board нет, просматривает все файлы `.md` в поиске шаблонов `**Agent**: {name}`, строк `Agent: {name}` или имён файлов, содержащих `_agent` или `-agent`.

4. **Подсчёт ходов:** для каждого обнаруженного агента читает файлы `progress-{agent}.md` и извлекает номер хода из шаблонов `turn: N`.

5. **Лента активности:** перечисляет 5 недавно изменённых файлов `.md`, извлекает последнюю содержательную строку (заголовки, строки статуса, пункты действий) как сообщение активности. Веб-дашборд также предоставляет страницу recap по адресу `/recap`.

## Что показывает каждый дашборд

### Статус сессии

Верхний блок показывает:
- **ID сессии:** извлекается из файлов сессии (формат `session-YYYYMMDD-HHMMSS`);
- **Статус:** цветовая индикация: зелёный для RUNNING, голубой для COMPLETED, красный для FAILED, жёлтый для UNKNOWN.

### Task board

Таблица агентов содержит каждого найденного агента:
- **Имя агента:** идентификатор домена (backend, frontend, mobile, qa, debug, pm);
- **Статус:** текущее состояние с визуальным индикатором (running/completed/failed/blocked/pending);
- **Ход:** текущий номер хода агента (количество завершённых итераций), извлекаемый из файлов прогресса;
- **Задача:** краткое описание работы агента (обрезается по ширине).

### Прогресс агента

Прогресс отслеживается по файлам `progress-{agent}.md`. Агент обновляет каждый файл во время работы. Дашборд читает из них:
- номер хода (увеличивается по мере продвижения агента);
- текущее действие (что агент делает сейчас);
- промежуточные результаты (частичные завершённые этапы).

### Результаты

После завершения агент записывает `result-{agent}.md`, содержащий:
- итоговый статус (COMPLETED или FAILED);
- список изменённых файлов;
- возникшие проблемы;
- созданные результаты.

Дашборд определяет завершение по наличию этого файла и обновляет статус агента.

## Runbook устранения неполадок

### Сигнал 1: агент показывает «running», но ход не меняется

**Симптом:** дашборд показывает, что агент работает, но номер хода не меняется несколько минут.

**Возможные причины:**
- агент застрял на долгой операции (большое сканирование кодовой базы или медленный вызов API);
- агент завершился с ошибкой, но PID-файл всё ещё существует;
- агент ждёт пользовательского ввода (в режиме auto-approve этого происходить не должно).

**Действия:**
1. Проверьте log-файл агента: `cat /tmp/subagent-{session-id}-{agent-id}.log`
2. Проверьте, действительно ли процесс работает: `oma agent status {session-id} {agent-id}`
3. Если процесс не работает, но статус показывает «running», агент завершился с ошибкой. Запустите его повторно с контекстом ошибки.

### Сигнал 2: агент показывает «crashed»

**Симптом:** `oma agent status` возвращает `crashed`.

**Возможные причины:**
- процесс CLI-вендора неожиданно завершился (нехватка памяти, исчерпан лимит API, сетевой тайм-аут);
- рабочий каталог агента был удалён или права доступа изменились;
- CLI вендора не установлен или не аутентифицирован.

**Действия:**
1. Проверьте log-файл и найдите причину: `cat /tmp/subagent-{session-id}-{agent-id}.log`
2. Проверьте установку CLI: `oma doctor`
3. Проверьте аутентификацию: `oma auth status`
4. Запустите агента повторно с той же задачей: `oma agent spawn {agent-id} "{task}" {session-id} -w {workspace}`

### Сигнал 3: дашборд показывает «no agents detected yet»

**Симптом:** дашборд запущен, но агентов не показывает.

**Возможные причины:**
- workflow ещё не дошёл до шага запуска агентов;
- каталог `.agents/state/memories/` пуст;
- дашборд следит не за тем каталогом.

**Действия:**
1. Проверьте каталог памяти: `ls -la .agents/state/memories/`
2. Убедитесь, что workflow не находится на этапе планирования (агенты ещё не запущены).
3. Проверьте, что дашборд использует правильный каталог проекта: CLI дашборда разрешает каталог памяти относительно текущего рабочего каталога.
4. При использовании другого пути: `MEMORIES_DIR=/path/to/.agents/state/memories oma dashboard terminal`

### Сигнал 4: веб-дашборд показывает «disconnected»

**Симптом:** индикатор подключения в браузере красный и показывает «Disconnected».

**Возможные причины:**
- процесс `oma dashboard web` завершён;
- браузер использует устаревший URL или в нём отсутствует токен запуска;
- порт занят другим процессом.

**Действия:**
1. Проверьте, работает ли процесс дашборда: `ps aux | grep dashboard`
2. Откройте точный URL с токеном, который вывел процесс; не удаляйте токен.
3. Попробуйте другой порт: `DASHBOARD_PORT=8080 oma dashboard web`
4. Проверьте доступность порта: `lsof -i :9847`
5. Веб-дашборд автоматически переподключается с экспоненциальной задержкой (начинается с 1 секунды, максимум 10 секунд). Подождите несколько секунд.

## Чек-лист мониторинга перед слиянием

Перед завершением мультиагентной сессии проверьте через дашборд:

- [ ] **Все агенты показывают «completed»:** нет агентов в состоянии «running» или «blocked».
- [ ] **Нет агентов в состоянии «failed»:** если такой есть, проверьте логи и запустите его повторно.
- [ ] **QA-агент завершил ревью:** найдите `result-qa-agent.md` или `result-qa.md`.
- [ ] **Нет результатов CRITICAL/HIGH:** проверьте файл QA с количеством результатов по серьёзности.
- [ ] **Статус сессии COMPLETED:** файл сессии должен показывать итоговый статус.
- [ ] **Лента активности содержит итоговый отчёт:** последняя активность должна быть сводкой.

---

## Критерии завершения

Мониторинг через дашборд завершён, когда:
1. Все запущенные агенты достигли конечного состояния (completed или failed-and-handled).
2. Цикл ревью QA завершён без блокирующих проблем.
3. Статус сессии отражает итог.
4. Результаты записаны в память для будущего использования.

## Технические детали

### Терминальный дашборд (oma dashboard terminal)

- **Наблюдение за файлами:** используется [chokidar](https://github.com/paulmillr/chokidar) с `awaitWriteFinish` (порог стабильности 200 мс, интервал опроса 50 мс), чтобы не отображать частично записанные файлы.
- **Рендеринг:** весь терминал очищается и перерисовывается при каждом событии chokidar. Для ANSI-цветов используются `picocolors`, а для рамки — Unicode-символы.
- **Каталог памяти:** разрешается из `MEMORIES_DIR`, затем из аргумента CLI дашборда, затем из `{cwd}/.agents/state/memories`.
- **Корректное завершение:** перехватывает `SIGINT` и `SIGTERM`, закрывает наблюдатель chokidar и завершается без ошибок.

### Веб-дашборд (oma dashboard web)

- **HTTP-сервер:** Node.js `createServer` обслуживает HTML-страницу по `/`, страницу recap по `/recap`, состояние JSON по `/api/state` и данные recap по `/api/recap`. Сервер привязывается к `127.0.0.1`.
- **WebSocket:** использует библиотеку `ws`. Соединение loopback-origin должно содержать токен процесса в query string. При подключении клиент сразу получает полное состояние. Последующие обновления отправляются как сообщения `{ type: "update", event, file, data }`.
- **Наблюдение за файлами:** используется та же конфигурация chokidar, что и в терминале. При изменении файла функция `broadcast()` собирает текущее состояние и отправляет его всем подключённым клиентам WebSocket.
- **Debouncing:** обновления группируются с задержкой 100 мс, чтобы не перегружать клиентов при быстрых последовательных записях (например, когда несколько агентов одновременно обновляют прогресс).
- **Автопереподключение:** клиент браузера переподключается с экспоненциальной задержкой (начальная 1 секунда, множитель 1,5, максимум 10 секунд), когда WebSocket-соединение разрывается.
- **Порт:** по умолчанию 9847, настраивается через переменную окружения `DASHBOARD_PORT`. API-запросы принимают `X-OMA-Dashboard-Token` или `?token=...`; при отсутствии или неверном токене возвращают `401`.
- **Построение состояния:** функция `buildFullState()` собирает сведения о сессии, task board, статусе агентов, количестве ходов и ленте активности в один объект JSON при каждом обновлении.
