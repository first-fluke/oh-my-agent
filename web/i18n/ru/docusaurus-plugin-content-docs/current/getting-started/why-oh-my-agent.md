# Зачем нужен oh-my-agent

oh-my-agent добавляет принадлежащий репозиторию слой вокруг CLI агентов, которыми уже пользуется ваша команда. В каталоге `.agents/` хранятся [навыки](./glossary.md#skill), [рабочие процессы](./glossary.md#workflow), [определения агентов](./glossary.md#agent-definition), правила и конфигурация моделей. Файлы, нужные конкретным поставщикам, создаются из этого [источника истины](./glossary.md#ssot), поэтому поведение можно проверять и менять вместе с проектом.

## Выбирайте его, когда репозиторию нужен координационный слой

OMA подходит, если вам нужно одно или несколько из следующего:

- **Несколько хостов или поставщиков агентов.** `model_preset: auto` использует нативную конфигурацию текущего runtime. Фиксированные и пользовательские пресеты могут направлять роли к другим поставщикам; `oma agent spawn` выполняет ненативную диспетчеризацию.
- **Повторяемый командный рабочий процесс.** `/work` ведёт одну ограниченную задачу, `/orchestrate` координирует делегированную работу, `/ultrawork` запускает параллельную работу с этапами ревью, а `/ralph` повторяет задачу с явно выделенной фазой judge.
- **Инструкции, принадлежащие репозиторию.** Навыки, рабочие процессы, правила и определения агентов находятся рядом с кодом. `oma link` проецирует выбранные файлы в форматы поддерживаемых поставщиков.
- **Механические проверки и долговечные результаты.** Запуски агентов могут записывать структурированные квитанции состояния и результата, а `oma verify agent <agent-type>` и `oma docs verify` дают явные проверки.

Если проект использует один хост и ему не нужны общие навыки, рабочие процессы или маршрутизация поставщиков, дополнительные файлы `.agents/` и команды CLI могут не оправдать настройку. OMA — это слой координации; он не заменяет модель хоста, редактор или критерии приёмки конкретного проекта.

## Проверка запускается выбранной вами командой

Запускайте `oma verify agent <agent-type> --workspace <path>`, когда нужны проверки для роли backend, frontend, mobile, QA, debug или planning. Верификатор объединяет статические проверки с настроенными командами: тестами, проверкой типов, SQL-проверками или `flutter analyze`; см. [`cli/commands/verify/report.ts`](https://github.com/first-fluke/oh-my-agent/blob/main/cli/commands/verify/report.ts). Отчёт показывает результат каждой проверки. Успешное прохождение этих проверок само по себе не доказывает, что функция отвечает продуктовым или предметным требованиям, поэтому критерии приёмки задачи всё равно нужно пересмотреть.

`/ralph` добавляет отдельную фазу [judge](./glossary.md#judge), если выбрать этот рабочий процесс. Она повторно проверяет заявленные критерии на каждой итерации и сохраняет артефакты рабочего процесса; это не шлюз, который запускается для каждого обычного запроса. Загрузка навыка также не запускает автоматически каждый рабочий процесс или команду проверки.

## Диспетчеризация остаётся видимой

`oma doctor --profile` показывает разрешённые поставщика и модель для каждой роли диспетчеризации. `oma agent spawn <agent-id> <prompt> <session-id>` — явный путь через CLI, когда текущий хост не обрабатывает роль сам. Правила разрешения модели и поведение конкретных поставщиков описаны в [«Важных настройках по умолчанию»](./important-defaults.md) и [«Моделях для агентов»](../guide/per-agent-models.md).

Хуки могут активировать рабочий процесс только при включённой интеграции соответствующего хоста. Нативную маршрутизацию навыков выполняет хост, а маршрутизация рабочих процессов следует выбранному рабочему процессу или хуку; обычный prompt не гарантирует запуск конкретного навыка или шлюза.

Необязательные средства координации описаны в [ограничении квоты сессии](../guide/configuration-reference.md#session-quota-caps), [цикле повторов и исследования `/orchestrate`](../core-concepts/workflows.md#orchestrate) и [назначении workspace](../core-concepts/parallel-execution.md#workspace-aware-pattern).

## Практический компромисс

OMA даёт команде общее место для определения маршрутизации, шагов выполнения, проверок и выходных файлов. Взамен команда должна поддерживать конфигурацию репозитория в актуальном состоянии и решить, какие рабочие процессы или команды проверки входят в её контракт приёмки. Этот компромисс полезен, когда согласованность между участниками важнее минимально возможной установки.

Исходное обсуждение позиционирования см. в [issue #155](https://github.com/first-fluke/oh-my-agent/issues/155#issuecomment-4142133589).
